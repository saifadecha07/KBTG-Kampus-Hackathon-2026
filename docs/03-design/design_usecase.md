## Decision Summary ล่าสุด

รายละเอียดเหตุผลและ warnings อยู่ใน [`decision_log.md`](decision_log.md) สรุปกฎที่ปิดแล้วสำหรับการ implement ไว้ตรงนี้:

- **Pace ล่ม:** ใช้ Fail-open ให้จ่าย/โอนจากบัญชีหลักได้ แต่หยุด Auto-Split, Backfill และถอนกระเป๋านิรภัย; รายการช่วงล่มเป็น `outside_pace` และ reconcile ภายหลัง
- **เงินกันบิลขาด:** อนุญาตให้เกิดได้ระหว่างระบบล่ม, ทำเครื่องหมาย `underfunded`, แล้วกันยอดขาดในเงินเข้ารอบถัดไปตาม Priority ของผู้ใช้
- **เงินตีกลับ:** reverse จากเงินที่เหลือทุกกระเป๋าโดยไม่รอ cooldown; ส่วนที่ขาดเป็น `reversal_shortfall` ให้ธนาคารจัดการ dispute ห้ามสร้างหนี้ใน Pace
- **บิล:** ผู้ใช้กำหนด Priority เอง; ผู้รับเดียวกันที่อาจเป็นหลายบิลต้องให้ผู้ใช้ยืนยัน; กลุ่มที่ยังไม่ยืนยันห้ามกันเงิน
- **บิลรายไตรมาส/รายปี:** ผู้ใช้เลือกเองว่าจะกันเต็มก้อนหรือทยอยกัน และต้องยืนยันก่อนบันทึก
- **กระเป๋านิรภัย:** ปิดกระเป๋ายังต้องรอ cooldown; ปิดบัญชีธนาคารทั้งบัญชีคืนเงินตามกระบวนการธนาคาร
- **Daily Target:** แก้กลางรอบมีผลวันถัดไป; ถ้าเพิ่มสูงกว่าความสามารถของบัญชีต้องยืนยันคำเตือน และเติมได้เท่าที่มี
- **เงินเข้าหลายก้อน:** แยกตาม transaction ID แต่รวมรายการค้างไว้ใน UI เดียว ไม่รวมยอดและไม่ re-split; pending item มี `due_date` แบบ nullable และไม่ผูกกับ `cycle_id` — ไม่มี deadline อยู่ passive queue, มี deadline จึงเข้า escalation
- **PoC:** รองรับ mock โอน/สแกนจ่าย/จ่ายบิล; ATM และบัตรเดบิตเป็น `outside_pace` และอยู่นอก PoC
- **Data Model:** ใช้ scope J2 ครบ entity สำคัญ โดย Ledger เป็น source of truth; บัญชีหลักแยก `balance`, `reserved`, `pending_unsplit` และคำนวณ `available = balance - reserved - pending_unsplit`

> ⚠️ **ยังไม่ปิด:** tech stack, API contract, field-level schema, demo time model, dispute workflow และรายละเอียด UX ของการถาม Priority เมื่อเงินไม่พอ — ต้องถามก่อนออกแบบต่อ

## 💵 กฎเงินพื้นฐาน (M1–M12) — ใช้ร่วมทุก UC

> ส่วนนี้คือกฎที่ **ทุก UC ต้องเคารพเหมือนกันหมด** ถ้าไม่กำหนดตรงนี้ แต่ละ UC จะคำนวณเงินคนละแบบแล้วยอดเพี้ยนโดยไม่มีใครรู้
> นี่คือจุดที่ Track 1 ได้เปรียบที่สุด — กรรมการสาย engineering ถามเรื่องพวกนี้แน่ และทีมที่ทำแค่ concept ตอบไม่ได้

### M1 — เก็บเงินเป็นจำนวนเต็ม "สตางค์" ห้ามใช้ทศนิยมลอยตัว

เก็บทุกจำนวนเงินเป็น **integer หน่วยสตางค์** (22,500.00 บาท = `2250000`) ใช้ int64
**ห้ามใช้ `float`/`double` กับเงินเด็ดขาด** — `0.1 + 0.2 != 0.3` ในเลขทศนิยมลอยตัว พอคูณด้วยการเติมเงินวันละครั้ง 30 วัน ยอดจะเพี้ยนสะสมจนกระทบยอดจริง
แปลงเป็นบาทเฉพาะตอนแสดงผลเท่านั้น

### M2 — การแบ่ง % ปัดลง เศษที่เหลือเข้าบัญชีรายเดือนเสมอ

1. คำนวณทุกกระเป๋าเป็นสตางค์แล้ว **ปัดลง (floor)**
2. เอายอดตั้งต้น ลบผลรวมที่ปัดแล้ว = **เศษ**
3. **เศษทั้งหมดเข้าบัญชีรายเดือน** (บัญชีรายเดือนเป็น "กระเป๋าเศษ" ของระบบ)

ตัวอย่าง: แบ่ง 10,000.01 บาท (`1000001` สตางค์) นิรภัย 20% · รายเดือน 80%
- นิรภัย = floor(1000001 × 0.20) = `200000` (2,000.00)
- รายเดือน = floor(1000001 × 0.80) = `800000` (8,000.00)
- เศษ = 1000001 − 200000 − 800000 = `1` สตางค์ → **เข้าบัญชีรายเดือน** เป็น `800001`

**ทำไมเศษต้องไม่เข้านิรภัย:** เงินที่เข้านิรภัยติด cooldown ทันที ถ้าเศษเข้าไปด้วย = ผู้ใช้โดนล็อกเงินมากกว่าที่ตั้งใจแม้แค่สตางค์เดียว ซึ่งอธิบายยากและผิดหลัก "ผู้ใช้ยินยอมตามที่ตั้งไว้"

### M3 — เป้ารายวันปัดลงเป็นจำนวนเต็มบาท

`14,640 ÷ 30 = 488.00` พอดี แต่ `14,640 ÷ 28 = 522.857…` → **เสนอ 522 บาท/วัน** (ปัดลงเป็นบาทเต็ม)
เศษที่เหลือ (`14,640 − 522×28 = 24 บาท`) **ค้างอยู่ในบัญชีรายเดือน ไม่หายไปไหน** และถูกใช้เป็นตาข่ายรองรับตอน backfill
เหตุผลที่ปัดลง: เป้าที่เป็นเลขกลมอ่านง่ายกว่า และปัดลงทำให้เงินไม่ขาดกลางรอบ

### M4 — Invariant: ผลรวมต้องตรงเสมอ (กฎข้อสำคัญที่สุด)

```
ยอดบัญชีหลัก + บัญชีรายเดือน + กระเป๋ารายวัน + กระเป๋านิรภัย = ยอดเงินรวมของผู้ใช้
```

ต้องเป็นจริง **ทุกวินาที หลังทุกธุรกรรม ไม่มีข้อยกเว้น**

- ในเทส: assert ข้อนี้หลัง**ทุก** operation
- ทดสอบด้วยการสุ่มธุรกรรม 10,000 รายการ (เงินเข้า · จ่าย · backfill · ขอถอน · ยกเลิก · cron) แล้วเช็คว่า invariant ไม่เคยพัง — **นี่คือหลักฐานคุณภาพชิ้นที่แข็งแรงที่สุดที่พิชได้ และทีม concept-only ทำไม่ได้**
- ใน production ต้องมี reconciliation job เทียบยอด Pace กับยอดจริงของธนาคารเป็นระยะ

### M5 — ห้ามกระเป๋าไหนติดลบ

ทุกกระเป๋ามีเงื่อนไข `balance >= 0` ระดับฐานข้อมูล
เงินต้องถูก **เติมเข้ากระเป๋าก่อน** แล้วค่อยหัก (UC-06) ไม่ใช่หักให้ติดลบแล้วค่อยตามเติม — ถ้าเขียนสลับลำดับ จะมีช่วงเวลาสั้น ๆ ที่ยอดติดลบ แล้วธุรกรรมอื่นที่เข้ามาพร้อมกันจะเห็นยอดผิด

### M6 — Ledger เขียนอย่างเดียว สองขาเสมอ

ทุกการเคลื่อนเงินบันทึกเป็นรายการ ledger ที่มี **ขาออกและขาเข้าคู่กัน** (จากกระเป๋าไหน ไปกระเป๋าไหน เท่าไหร่ เมื่อไหร่ เพราะอะไร)

- **ห้าม `UPDATE balance` ตรง ๆ โดยไม่เขียน ledger**
- ยอดคงเหลือของกระเป๋าต้อง**คำนวณกลับจาก ledger ได้เสมอ** (เก็บเป็น cache ได้ แต่ต้องตรวจสอบย้อนได้)
- ledger **แก้ไม่ได้ ลบไม่ได้** — การยกเลิกทำด้วยการเขียนรายการกลับทาง ไม่ใช่ลบของเดิม
- ได้ผลพลอยได้คือหน้าประวัติให้ผู้ใช้ดูย้อนหลัง และ audit trail ตาม PDPA

### M7 — ทุกชุดการเคลื่อนเงินเป็น transaction เดียว

backfill + หักเงินซื้อ = **1 transaction** ล้มก็ล้มทั้งชุด ไม่มีสถานะครึ่ง ๆ (ผูกกับ L11)
ห้ามมีจังหวะที่เงินออกจากกระเป๋าหนึ่งแล้วยังไม่เข้าอีกกระเป๋าหนึ่ง

### M8 — เวลาและเส้นแบ่งวัน (ปิด L7)

- เก็บ timestamp ทั้งหมดเป็น **UTC** แสดงผลเป็น **Asia/Bangkok**
- "วัน" ของ Pace = `00:00:00.000` ถึง `23:59:59.999` ตามเวลา Asia/Bangkok
- ธุรกรรมนับเข้าวันไหน ใช้ **เวลาที่ ledger commit ที่ server** ไม่ใช่เวลาที่ผู้ใช้กด ไม่ใช่เวลาเครื่อง
- cron เติมกระเป๋ารายวันรันที่ `00:00` ของ Asia/Bangkok · ถ้ารันช้าไป เช่น `00:05` ยังนับเป็นรอบของวันนั้น (ใช้ **วันที่** เป็น idempotency key ไม่ใช่เวลาที่รันจริง)
- **ไทยไม่มี daylight saving** จึงไม่มีปัญหาวันซ้ำ/วันหาย แต่ต้องเขียนไว้ว่าใช้ timezone เดียวตายตัว

### M9 — "เงินกันบิล" เป็นยอดจอง ไม่ใช่ยอดคงเหลือ

เงินบิลและเงินเข้าที่ยังไม่แบ่งอยู่ในบัญชีหลักโดยไม่ถูกกวาด — แปลว่าบัญชีหลักต้องมี **3 ตัวเลข** ไม่ใช่ตัวเดียว:

| ฟิลด์ | ความหมาย |
|---|---|
| `balance` | เงินที่มีอยู่จริง |
| `reserved` | ยอดที่ Pace กันไว้จ่ายบิล |
| `pending_unsplit` | ยอดเงินเข้าที่ยังไม่แบ่งทั้งหมด ไม่ผูกกับ `cycle_id` และไม่มีวันหมดอายุ |
| `available` | `balance − reserved − pending_unsplit` = เงินที่ใช้ได้จริง |

- ตอนบิลหักจริง → `balance` ลด และ `reserved` ลดพร้อมกันเท่ากัน
- ตอนสร้าง pending income → `pending_unsplit` เพิ่ม; ตอนผู้ใช้จัดการก้อนเงินสำเร็จหรือมี reversal → `pending_unsplit` ลดตาม transaction ID
- การเปลี่ยน `reserved` หรือ `pending_unsplit` เป็นการเปลี่ยนสถานะเงินที่ต้องมี audit trail และ ledger classification entry แบบสองขา ภายใน transaction เดียวตาม M6/M7 แม้ `balance` จริงจะไม่ขยับ
- `reserved` จาก G12 ต้อง recompute ตามบิลที่เข้าเงื่อนไข ไม่ใช้การบวกสะสม เพื่อให้ cron รันซ้ำแล้วผลเท่าเดิม
- ผู้ใช้ต้องเห็น `balance`, `reserved`, `pending_unsplit` และ `available` แยกกัน ห้ามโชว์แค่ `balance` เพราะผู้ใช้จะคิดว่ามีเงินใช้มากกว่าจริง

### M10 — Server เป็นแหล่งความจริงเดียว

ทุกจำนวนเงินที่แสดงบนแอปต้องมาจาก server เท่านั้น — client **ห้ามคำนวณยอดเอง** แล้วเอาไปแสดงหรือส่งกลับ (หลักเดียวกับ cooldown ใน UC-07)

### M11 — ตรวจค่าที่รับจาก client ทุกครั้งที่ฝั่ง server

จำนวนเงินที่รับมาต้อง: เป็นจำนวนเต็มสตางค์ · มากกว่า 0 · ไม่เกินยอดที่มีจริง · ไม่เกินเพดานที่สมเหตุสมผล
% ที่รับมาต้องรวมได้ 100 พอดี **ตรวจซ้ำที่ server เสมอ** แม้ UI จะบังคับไว้แล้ว

### M12 — การแสดงผลต้องตรงกับที่เก็บ

แสดงทศนิยม 2 ตำแหน่งเสมอ ห้ามปัดให้สวยแล้วต่างจากยอดจริง
ถ้ายอดจริงคือ 488.33 ห้ามแสดง 488 — ผู้ใช้บวกเลขเองแล้วไม่ตรงจะเสียความเชื่อถือทันที

## กลไกเรียนรู้บิล (ใช้ร่วมทุก UC)

> "กันเงินบิลไว้ก่อนเสมอ" คือลำดับความสำคัญอันดับ 1 ของ Pace — ส่วนนี้คือกฎที่บอกว่าระบบรู้ได้ยังไงว่ารายการไหนคือบิล กันเท่าไหร่ และครบกำหนดวันไหน
> ทุกกฎเป็นเลขคณิตล้วน ไม่มี ML ไม่มีการเดา ผลลัพธ์เดิมทุกครั้งจากข้อมูลชุดเดิม — เขียน unit test ได้ 1:1

### B1 — นิยาม "บิล"

รายการจ่ายออกจะถูกนับเป็นบิลเมื่อครบทุกข้อ:

| เกณฑ์ | ค่า | เหตุผล |
|---|---|---|
| ผู้รับคนเดิม | — | จัดกลุ่มตามผู้รับ |
| จำนวนรอบที่จ่ายมาแล้ว | ≥ 3 | ต่ำกว่านี้ยังแยกไม่ออกว่าเป็นบิลหรือบังเอิญ |
| ยอดกลาง (median) | ≥ 300 บาท | กันรายการจิปาถะ |
| วันที่ในเดือนที่จ่าย | ห่างจาก "วันประจำ" ไม่เกิน 7 วัน | ดู B2 |
| ความถี่ | เดือนละ 1 ครั้ง | กันกาแฟทุกเช้า / ค่ารถทุกวัน ให้ตกเกณฑ์ |
| ความครอบคลุม | ≥ 75% ของเดือนในช่วงที่ดู | บิลที่จ่ายบ้างไม่จ่ายบ้างไม่ถือเป็นบิล |

รายการที่หักผ่านบัตรเครดิต/เดบิตไม่เข้าเกณฑ์นี้ (ดู B5)

### B2 — ต้องดู "วันที่ในเดือน" ไม่ใช่ "ระยะห่างเป็นวัน"

คนจ่ายค่าเช่าด้วยมือ ตัวอย่างจริง: จ่ายวันที่ 3, 8, 3, 3, 4 → ระยะห่างระหว่างงวดคือ 36 วันและ 25 วัน

ถ้าตัดสินด้วยระยะห่างเป็นวัน (คาดหวัง ~30 วัน) รายการนี้จะ**ตกเกณฑ์ทั้งหมด** ทั้งที่เป็นค่าเช่าชัดเจน

วิธีที่ใช้: หา "วันประจำ" = วันที่ในเดือนที่ทำให้ระยะห่างรวมจากทุกงวดน้อยที่สุด แล้ววัดว่าทุกงวดห่างจากวันประจำไม่เกิน 7 วัน (การวัดต้องวนรอบเดือน — วันที่ 30 กับวันที่ 2 ห่างกัน 2 วัน ไม่ใช่ 28 วัน)

### B3 — กันเงินเท่าไหร่

ดู 6 รอบล่าสุดของบิลนั้น แล้วแยกเป็นสองแบบ:

| แบบ | เงื่อนไข | ยอดที่กัน |
|---|---|---|
| **บิลคงที่** (ค่าเช่า ค่าผ่อน) | ยอดแกว่ง < 15% | `max(ยอดล่าสุด, ยอดกลาง)` |
| **บิลผันผวน** (ค่าไฟ ค่าน้ำ) | ยอดแกว่ง ≥ 15% | percentile 75 ของ 6 รอบล่าสุด |

`max(ยอดล่าสุด, ยอดกลาง)` แก้สองเคสพร้อมกัน:
- **ค่าเช่าขึ้นราคา** → ตามทันตั้งแต่งวดแรกที่ขึ้น ไม่ต้องรอค่ากลางขยับ
- **เดือนไหนจ่ายน้อยผิดปกติ** (จ่ายขาด/จ่ายบางส่วน) → ไม่ลดยอดที่กันตาม

percentile 75 สำหรับบิลผันผวน = เอียงไปทางกันเกินไว้ก่อน เพราะกันขาดแล้วบิลเด้ง เสียหายกว่ากันเกินแล้วเงินค้าง

กฎนี้ทำให้ edge case "บิลหักจริงมากกว่าที่กันไว้" ใน UC-02 เกิดน้อยลงมาก แต่ยังต้องมี backfill ไว้เป็นตาข่ายรองรับ

### B4 — เดือนคาบเกี่ยว และสถานะบิล

**เดือนคาบเกี่ยว** — ค่าเช่าครบกำหนดวันที่ 1 แต่จ่ายล่วงหน้าวันที่ 30 ของเดือนก่อน:

| กรณี | นับเป็นของเดือนไหน |
|---|---|
| วันประจำ ≤ 7 แต่จ่ายวันที่ ≥ 24 | เดือนถัดไป |
| วันประจำ ≥ 24 แต่จ่ายวันที่ ≤ 7 | เดือนก่อนหน้า |
| นอกนั้น | เดือนที่จ่าย |

ไม่มีกฎนี้ ระบบจะคิดว่าเดือนนั้นจ่ายค่าเช่าสองครั้ง แล้วกันเงินผิดทันที

**สถานะบิล** — บิลที่เลิกใช้แล้ว (ย้ายบ้าน ยกเลิกเน็ต) ต้องหยุดกันเงิน ไม่งั้นเงินจมทุกเดือน:

| สถานะ | เงื่อนไข | ระบบทำอะไร |
|---|---|---|
| `active` | ยังไม่เลยกำหนด หรือเลยไม่เกิน 7 วัน | กันเงินตามปกติ |
| `late` | เลยกำหนด 7 วัน ถึง 1 รอบบิล | ยังกันเงินไว้ + เตือนผู้ใช้ว่ายังไม่เห็นการจ่าย |
| `stopped` | เลยกำหนดเกิน 1 รอบบิล | หยุดกันเงิน คืนยอดที่กันไว้เข้าบัญชีรายเดือน + แจ้งผู้ใช้ |

### B5 — ข้อจำกัดที่ต้องยอมรับ (เขียนไว้ให้ชัด อย่าอ้างเกินจริง)

| ข้อจำกัด | ผลกระทบ | ทางออก |
|---|---|---|
| **บิลที่หักผ่านบัตร** (Netflix, Spotify, ค่าเน็ตผูกบัตร) มองไม่เห็นในรายการเดินบัญชี เพราะไม่มีชื่อร้าน | กันเงินให้ไม่ได้เลย | ผู้ใช้เพิ่มเอง — UC-13 |
| **บิลใหม่ต้องจ่ายครบ 3 รอบ** ระบบถึงรู้จัก | เดือนแรก ๆ ที่ผูกบิลใหม่ ระบบยังไม่กันเงินให้ | ผู้ใช้เพิ่มเอง — UC-13 |
| **บิลรายปี** (ประกัน ค่าเทอม ภาษี) ระบบเรียนรู้เองจากประวัติยังไม่รองรับ | ระบบจะตรวจเจอเองไม่ได้จากข้อมูลย้อนหลังแบบ B1–B4 | ผู้ใช้เพิ่มเองผ่าน UC-13 และเลือกกันเต็มก้อนหรือทยอยกัน; การตรวจเจออัตโนมัติเป็นงานเฟสถัดไป |

> ⚠️ สองข้อแรกแปลว่า **คำอ้าง "กันเงินบิลไว้ก่อนเสมอ" จะไม่จริงถ้าไม่มี UC-13** — ปุ่มให้ผู้ใช้เพิ่มบิลเองไม่ใช่ของเสริม แต่เป็นส่วนที่ทำให้กลไกสมบูรณ์

## UC-01 — ตั้งค่าครั้งแรก (Onboarding)

**Actor:** ผู้ใช้ใหม่
**Precondition:** ยังไม่เคยเปิดใช้ Pace

**Steps**
1. เปิดเมนู Pace ใน K PLUS
2. **ระบบอ่านรายการเดินบัญชีย้อนหลังตามกฎ B1–B4 แล้วแสดงบิลที่เจอให้ผู้ใช้ยืนยัน**
   - *"เจอบิลประจำ 3 รายการ: ค่าเช่า 3,500 (ทุกวันที่ 3) · ค่าไฟ ~900 (ทุกวันที่ 20) · ค่าเน็ต 600 (ทุกวันที่ 5)"*
   - ผู้ใช้ติ๊กออกรายการที่ไม่ใช่บิล · แก้ยอด/วันที่ได้ · **กดเพิ่มบิลที่ระบบมองไม่เห็นได้ (UC-13)**
   - ถ้าประวัติไม่พอ (บัญชีใหม่ / ไม่ถึง 3 รอบ) → ข้ามขั้นนี้ ให้ผู้ใช้กรอกเองทั้งหมด
3. ระบบถาม: รายได้ประมาณเท่าไหร่ / เข้าวันไหน / มีค่าเช่าไหม / ผ่อนอะไรอยู่ไหม *(ข้อที่ระบบเจอจากข้อ 2 แล้วให้เติมมาให้ล่วงหน้า)*
4. ระบบเสนอ **"First Jobber Starter Split"**: บิล/ค่าเช่า 40% · นิรภัย 20% · ใช้จ่ายรายวัน 40%
5. ผู้ใช้กดรับ หรือปรับ % เอง (รวมต้องได้ 100%)
6. **เปิดบัญชีนิรภัย (ประเภทบัญชีพิเศษ — สมัครใจ)**
   - ตั้งชื่อ (default: "กองทุนตั้งตัว")
   - **ตั้งความยาว cooldown ครั้งเดียว ณ ตอนนี้** (เช่น 24 ชม.) — แสดงเงื่อนไขชัดเจน + ให้ติ๊กยอมรับ
   - ⚠️ **ตั้งแล้วแก้ไม่ได้** ถ้าอยากได้ค่าอื่นต้องปิดบัญชีแล้วเปิดใหม่ (ซึ่งเงินก็ต้องผ่าน cooldown)

**Expected:** สร้าง ePocket 3 บัญชี + บันทึก SplitRule + DailyTargetConfig + **CooldownPolicy (immutable)** + **รายการบิลที่ผู้ใช้ยืนยันแล้ว**

> 💡 **ทำไมต้องอ่านประวัติตั้งแต่ข้อ 2:** ผู้ใช้เห็นคุณค่าทันทีตั้งแต่จอแรก ("แอปรู้จักค่าเช่าฉันแล้ว") แทนที่จะต้องกรอกบิลเองทีละรายการ — และเป็นเงื่อนไขที่ทำให้แก้ปัญหา cold start ใน L9 ได้

> ⚖️ **เหตุผลเชิงกฎหมาย:** ทำแบบนี้ = ลูกค้าสมัครใจผูกพันตามเงื่อนไขของผลิตภัณฑ์เงินฝาก (หลักเดียวกับ **ฝากประจำ**) ไม่ใช่ธนาคารไปหน่วงเงินลูกค้าเอง — ต่างจากฝากประจำแค่หน่วยเป็นชั่วโมงแทนเดือน และไม่มีค่าปรับ

## UC-02 — เงินเข้า + แบ่งอัตโนมัติ (พนักงานประจำ)

**Actor:** พลอย
**Precondition:** ตั้งค่าแล้ว ยังไม่เคยติ๊ก "จำไว้" สำหรับผู้ส่งรายนี้

**Steps**
1. วันที่ 25 เงิน 22,500 เข้าบัญชี
2. **ระบบรวมยอดบิลที่จะครบกำหนดก่อนรอบเงินเข้าถัดไป** โดยใช้กฎ B1–B4 + บิลที่ผู้ใช้เพิ่มเอง (UC-13) → รวม 4,200
   | บิล | แบบ (B3) | ยอดที่กัน | ที่มา |
   |---|---|---|---|
   | ค่าเช่า | คงที่ | 1,300 | `max(ล่าสุด, กลาง)` |
   | ผ่อนมือถือ | คงที่ | 1,500 | `max(ล่าสุด, กลาง)` |
   | ค่าไฟ | ผันผวน | 800 | percentile 75 |
   | ค่าเน็ต (ผูกบัตร) | ผู้ใช้เพิ่มเอง | 600 | UC-13 |
   - นับเฉพาะบิลสถานะ `active` และ `late` — บิล `stopped` ไม่ถูกกัน (B4)
3. ระบบเด้ง: *"เงินเข้า 22,500 บาท — กันไว้จ่ายบิล 4,200 · แบ่งส่วนที่เหลือ 18,300 ตามแผนไหม?"* `[แบ่งเลย] [ไม่ใช่ตอนนี้]`
   - กดดูรายการบิลที่กันไว้ได้ · เพิ่มรายการที่จ่ายเอง (ไม่ได้ผูกหักอัตโนมัติ) ได้
   - มี checkbox: *"จำไว้ ทำอัตโนมัติทุกครั้งจากผู้ส่งนี้ (บริษัท ABC)"*
4. ผู้ใช้กด **แบ่งเลย** + ติ๊กจำไว้
5. **เงินบิล 4,200 อยู่ในบัญชีหลักเหมือนเดิม ไม่ถูกกวาด** → แบ่งเฉพาะ 18,300: นิรภัย 3,660 (20%) · บัญชีรายเดือน 14,640
6. ระบบคำนวณเป้ารายวัน: 14,640 ÷ 30 วัน → เสนอ *"แนะนำ 488 บาท/วัน"* `[ใช้ตัวนี้] [แก้เอง]`
7. ผู้ใช้กดรับ (หรือพิมพ์ 450 เอง)

**Expected:** ยอดทุกกระเป๋าถูกต้อง · **บัญชีหลักเหลือ ≥ 4,200 สำหรับบิล** · DailyTarget ล็อกทั้งรอบ · บันทึกผู้ส่งเป็น auto-approve · **มีปุ่ม "ยกเลิกการแบ่ง" ค้างอยู่ 15 นาทีหลังกด** (L13) กดแล้วเงินกลับไปกองที่บัญชีหลักทั้งหมด

**ลำดับความสำคัญ:** บิล (กันไว้ก่อนเสมอ) → นิรภัย → บัญชีรายเดือน → รายวัน

**Edge cases**
- **เงินเข้าไม่พอจ่ายบิลทั้งหมด** → กันบิลให้ได้มากที่สุดก่อน ที่เหลือค่อยแบ่ง (อาจได้นิรภัย 0) + เตือนผู้ใช้ชัดว่ารอบนี้ออมไม่ได้เพราะบิลกินหมด
- **ผูกบิลใหม่กลางรอบ** (หลังกวาดเงินไปแล้ว) → **ระบบยังไม่รู้จักบิลนั้น** (ต้องครบ 3 รอบตาม B1) จึงต้องอาศัยผู้ใช้กดเพิ่มเองผ่าน UC-13 → เมื่อเพิ่มแล้วระบบเตือน + เสนอดึงเงินคืนจากบัญชีรายเดือนมากันไว้
- **บิลหักจริงมากกว่าที่กันไว้** (ค่าไฟแพงกว่าปกติ) → ดึงส่วนต่างจากบัญชีรายเดือนมาเติมอัตโนมัติ (หลักเดียวกับ backfill UC-06) ห้ามปล่อยให้บิลเด้ง
- **บิลที่หายไป** → พอเข้าสถานะ `stopped` (B4) ยอดที่เคยกันไว้ถูกคืนเข้าบัญชีรายเดือน + แจ้งผู้ใช้ *"ไม่เห็นการจ่ายค่าเน็ต 2 รอบแล้ว — หยุดกันเงินให้แล้ว"*
- **เงินเข้าแล้วโอนออกเกือบหมดใน 24 ชม.** (เพื่อนโอนมาให้ฝากจ่าย) → ดู L5

**เดือนถัดไป:** เงินจากบริษัท ABC เข้า → **ไม่เด้งถาม** แบ่งอัตโนมัติทันที + แจ้งเตือนว่าแบ่งแล้ว

## UC-03 — เงินเข้า + แบ่ง (ฟรีแลนซ์)

**Actor:** น้ำ
**Precondition:** ตั้งค่าแล้ว ผู้ส่งเป็นลูกค้ารายใหม่ทุกครั้ง

**Steps**
1. ลูกค้าโอน 15,000 วันไหนก็ได้
2. ระบบเด้งถามแบบเดียวกับ UC-02
3. กด **แบ่งเลย** แต่ **ไม่ติ๊กจำไว้**
4. ระบบแบ่งตาม % เดิม: นิรภัย 3,000 · บัญชีรายเดือน 12,000
5. ระบบถาม *"ก้อนนี้ต้องใช้กี่วัน?"* (default 30) → แนะนำ 400 บาท/วัน
6. กดรับ

**Expected:** ทำงานด้วยโค้ดชุดเดียวกับ UC-02 ทุกประการ ต่างแค่ไม่บันทึก auto-approve
**หมายเหตุ:** ไม่มี ML ไม่มีการทายรายได้ ระบบไม่เดาอะไรเลย

## UC-04 — เติมกระเป๋ารายวัน (เที่ยงคืน)

**Actor:** ระบบ (cron)
**Precondition:** มี DailyTarget ตั้งไว้แล้ว

**Steps**
1. เที่ยงคืน ระบบเช็คยอดกระเป๋ารายวัน
2. ถ้ายอด < เป้า → ดึง **ส่วนต่าง** จากบัญชีรายเดือนมาเติมให้ครบเป้าพอดี
3. รีเซ็ตตัวเลข "เกินเป้าไปแล้ว X บาท" ของเมื่อวานเป็น 0

**Expected:**
- เป้า 600 · เหลือ 200 → เติม 400 (ไม่ใช่เติม 600 ทับ)
- เป้า 600 · เหลือ 600 (ไม่ได้ใช้เลย) → เติม 0
- **เงินเหลือสะสมข้ามวันได้ (carry-over)** เพราะเติมแค่ส่วนต่าง

## UC-06 — ใช้จ่ายเกินเป้า (Backfill + Warning)

**Actor:** ผู้ใช้
**Precondition:** กระเป๋ารายวันเหลือ 100 · เป้า 600 · บัญชีรายเดือนมี 17,400

**Steps**
1. ผู้ใช้จ่าย 450 บาท (เกินยอดที่มีในกระเป๋ารายวัน)
2. ระบบเช็คก่อนตัดเงิน → ไม่พอ ขาด 350
3. **ดึง 350 จากบัญชีรายเดือนมาเติมกระเป๋ารายวันก่อน** (atomic เดียวกับการตัดเงิน)
4. ตัดเงิน 450 จากกระเป๋ารายวัน → ธุรกรรมผ่านปกติ **ไม่ถูกบล็อก**
5. เด้ง warning: *"วันนี้ใช้เกินเป้าไป 350 บาท — บัญชีเงินรายเดือนเหลือ 17,050 บาท"*
6. บันทึกสถิติ: วันนี้เกิน 350 · นับเป็นวันที่เกินของเดือนนี้ +1
7. หน้ากระเป๋ารายวันโชว์ *"เกินเป้าไปแล้ว 350 บาท"* **ค้างตลอดวัน**

**Expected:**
- ธุรกรรมไม่เคยถูกปฏิเสธ ตราบใดที่บัญชีรายเดือนยังมีเงิน
- **ทุกธุรกรรมตัดจากกระเป๋ารายวันเสมอ ไม่สลับไปหักบัญชีรายเดือนโดยตรง**
- warning ต้องแสดงยอดคงเหลือบัญชีรายเดือนด้วย ไม่ใช่แค่ยอดที่เกิน

**Edge — บัญชีรายเดือนหมดจริง:** ธุรกรรมถูกปฏิเสธ (เงินหมดก็คือหมด) ต้องแจ้งชัด ห้าม crash / ห้ามเงียบ

## UC-07 — ขอถอนจากนิรภัย

**Actor:** ผู้ใช้
**Precondition:** นิรภัยมี 4,500 · cooldown 24 ชม.

**Steps**
1. กดขอถอน 1,000 บาท (ไม่มีขั้นต่ำ/สูงสุด)
2. ระบบสร้าง WithdrawRequest สถานะ `pending` · `release_at` = ตอนนี้ + 24 ชม.
3. **เงินยังอยู่ในนิรภัย** ยังไม่ตัดออก
4. เด้ง notification ทันที: *"ขอถอน 1,000 บาท — เงินจะเข้ากระเป๋ารายวันวันที่ ... เวลา ..."*
5. หน้านิรภัยโชว์สถานะรอ + นับถอยหลัง

**Expected:** ยอดนิรภัยยังเป็น 4,500 · มี request 1 รายการสถานะ pending

**สำคัญ:** cooldown คิดที่ **server เท่านั้น** client แค่แสดงผลจาก timestamp ที่ server ส่งมา — ห้ามคำนวณจากนาฬิกาเครื่อง

## UC-08 — ครบ cooldown ปล่อยเงินอัตโนมัติ

**Actor:** ระบบ
**Steps**
1. ก่อนครบกำหนด ~1 ชม. → เด้งเตือน *"อีก 1 ชม. เงิน 1,000 บาทจะเข้ากระเป๋ารายวัน"* (โอกาสสุดท้ายให้ยกเลิก)
2. ครบเวลา → ย้ายเงินเข้ากระเป๋ารายวันอัตโนมัติ **ไม่ต้องกดยืนยันซ้ำ**
3. สถานะเปลี่ยนเป็น `released`

**Expected:** นิรภัยเหลือ 3,500 · กระเป๋ารายวัน +1,000
**สำคัญ:** ถ้า push notification ส่งไม่สำเร็จ (มือถือปิด/ไม่มีเน็ต) **เงินต้องปล่อยตามเวลาเหมือนเดิม** ห้ามผูกการปล่อยเงินไว้กับความสำเร็จของ notification

## UC-10 — ขอถอนซ้ำตอนมีคำขอค้างอยู่

**Actor:** ผู้ใช้
**Precondition:** มี request 1,000 บาท รออยู่ เหลืออีก 2 ชม.

**Steps**
1. กดขอถอนเพิ่ม 500 บาท
2. ⚠️ ระบบต้อง **เตือนก่อน**: *"การขอถอนเพิ่มจะรีเซ็ตเวลารอของคำขอเดิม (จาก 2 ชม. เป็น 24 ชม.)"* `[ยืนยัน] [ยกเลิก]`
3. กดยืนยัน → รวมเป็นคำขอเดียว 1,500 บาท · นับเวลาใหม่ 24 ชม.

**Expected:** มี request เดียว ไม่ใช่สองรายการ · เวลาเริ่มนับใหม่
**เหตุผล:** กันช่องโหว่ทยอยถอนทีละน้อยถี่ๆ เพื่อเลี่ยง delay
**✅ ตัดสินแล้ว (A7):** ใช้ merge-timer แบบนี้ (รวมก้อนเดียว รีเซ็ตเวลา) ไม่แยก timer ต่อคำขอ — เพิ่มยอดรีเซ็ตเวลา แต่**ลดยอดไม่รีเซ็ตเวลา** (G31)

## UC-11 — ปิดบัญชีนิรภัย / เลิกใช้ Pace

**Actor:** ผู้ใช้
**Precondition:** นิรภัยมีเงินอยู่

**Steps**
1. กดปิดบัญชีนิรภัย
2. ระบบแจ้ง: *"เงิน X บาทจะเข้ากระเป๋ารายวันหลังครบ cooldown ตามเงื่อนไขที่ตกลงไว้ตอนเปิดบัญชี"*
3. สร้าง WithdrawRequest ยอดเต็ม → เข้าสถานะ pending เหมือน UC-07
4. ครบเวลา → เงินออก → บัญชีถูกปิด

**Expected:** การปิดกระเป๋านิรภัยไม่ใช่ทางลัดเลี่ยง cooldown — เงินยังต้องรอตามเงื่อนไขเดิม

**กรณีปิดบัญชีธนาคารทั้งบัญชี:** เป็นกระบวนการคนละกรณีกับการปิดกระเป๋านิรภัย หากผู้ใช้ปิดบัญชีธนาคารทั้งหมด ธนาคารต้องคืนเงินตามกระบวนการปิดบัญชีของธนาคารโดยไม่บังคับรอ cooldown ของ Pace

**ปิดเฉพาะ auto-split / daily refill:** ปิดได้ทันที ไม่มีเงื่อนไข (ไม่กระทบเงินที่ล็อกอยู่ในนิรภัย)

## UC-13 — จัดการบิลเอง (เพิ่ม / แก้ / ลบ)

**Actor:** ผู้ใช้
**Precondition:** ตั้งค่าแล้ว

> ⚠️ **ไม่ใช่ฟีเจอร์เสริม** — ตาม B5 มีบิลสองประเภทที่ระบบมองไม่เห็นเลย (หักผ่านบัตร · บิลใหม่ที่ยังไม่ครบ 3 รอบ) ถ้าไม่มีหน้านี้ คำอ้าง "กันเงินบิลไว้ก่อนเสมอ" จะไม่เป็นความจริง

**Steps — เพิ่มบิลเอง**
1. เปิดหน้าบิล → กด "เพิ่มบิล"
2. กรอก: ชื่อ · ยอด · วันที่ครบกำหนดในเดือน · รอบ (รายเดือน / รายไตรมาส / รายปี)
3. เลือกแบบ: **ยอดคงที่** (กันเท่าที่กรอก) หรือ **ยอดผันผวน** (กันเท่าที่กรอกไว้เป็นเพดาน แล้วให้ระบบปรับตาม B3 เมื่อเห็นการจ่ายจริงครบ 3 รอบ)
3.5. **ถ้าเลือกรอบรายไตรมาส/รายปี** → ระบบเสนอ **"ทยอยกันเฉลี่ย"** เป็นค่าเริ่มต้น พร้อมโชว์ยอดที่จะกันต่อรอบและยอดสะสมจนครบกำหนด — ผู้ใช้กดสลับเป็น **"กันเต็มก้อน"** ได้ก่อนกดยืนยัน (G41/R6)
4. บันทึก → บิลเข้าไปรวมในยอดที่กันตอนเงินเข้า (UC-02 ข้อ 2) รอบถัดไปทันที

**Steps — แก้ / ลบ**
- แก้ยอดหรือวันที่ได้ตลอด → มีผลกับรอบถัดไป ไม่ย้อนหลังกับเงินที่กันไปแล้ว
- ลบบิล → ยอดที่กันไว้ในรอบปัจจุบันคืนเข้าบัญชีรายเดือนทันที + แจ้งยอดที่คืน

**Expected**
- บิลที่ผู้ใช้เพิ่มเองและบิลที่ระบบเรียนรู้ **ใช้โค้ดชุดเดียวกันในการกันเงิน** ต่างแค่แหล่งที่มา
- หน้าบิลต้องแยกให้เห็นว่าอันไหนระบบเจอเอง อันไหนผู้ใช้เพิ่ม (ผู้ใช้ต้องรู้ว่าอะไรระบบดูแลให้แล้ว)
- บิลที่ผู้ใช้เพิ่มเอง **ไม่เข้าสถานะ `stopped` อัตโนมัติ** (ระบบมองไม่เห็นการจ่ายผ่านบัตรอยู่แล้ว จะตัดสินว่าเลิกแล้วไม่ได้) — ต้องให้ผู้ใช้ลบเอง

**Edge cases**
- **ผู้ใช้เพิ่มบิลที่ระบบเจออยู่แล้ว (ซ้ำ)** → เตือนว่าตรงกับบิลที่มีอยู่ ให้เลือกแก้ของเดิมแทนการเพิ่มใหม่ ห้ามกันเงินสองเท่าเงียบ ๆ
- **เพิ่มบิลย้อนหลังที่ครบกำหนดไปแล้วในรอบนี้** → ถามว่าจ่ายไปแล้วหรือยัง ถ้าจ่ายแล้วให้เริ่มกันรอบหน้า

## Logic Decisions (ตัดสินแล้ว; รายละเอียดการตัดสินใจล่าสุดอยู่ใน `decision_log.md`)

### 🔴 สำคัญ — ไม่มีในเอกสารเลย แต่เกิดขึ้นจริงทุกเดือน

**L1 — จบรอบแล้วขึ้นรอบใหม่ทำยังไงกับเงินที่เหลือ** — ✅ **ตัดสินแล้ว**

**กฎที่ใช้ — กวาดกลับก่อน แล้วค่อยแบ่งรอบใหม่ · เงินไม่หาย · ไม่มีอะไรเข้านิรภัยโดยที่ผู้ใช้ไม่ได้กด**

ตอนผู้ใช้ยืนยันการแบ่งรอบใหม่ (UC-02 ข้อ 4) ระบบทำตามลำดับนี้:

1. **กวาดเงินที่เหลือในกระเป๋ารายวันกลับเข้าบัญชีรายเดือน** ทั้งหมด (เช่น 1,200)
2. รวมกับยอดที่เหลือในบัญชีรายเดือน (2,000) และเงินก้อนใหม่ที่แบ่งได้ → เป็นยอดตั้งต้นของรอบใหม่
3. คำนวณเป้ารายวันรอบใหม่จาก **ยอดรวมทั้งหมด ÷ จำนวนวันในรอบใหม่**
4. **เสนอ (ไม่บังคับ):** *"รอบที่แล้วคุณเหลือ 3,200 บาท — เก็บเข้ากองทุนตั้งตัวไหม?"* `[เก็บเลย] [ใช้ต่อ]`

**เหตุผลที่ไม่โยกเข้านิรภัยอัตโนมัติ (ตัวเลือก ค เดิม):** เงินเข้านิรภัยติด cooldown ทันที ถ้าระบบโยกให้เองโดยผู้ใช้ไม่ได้กด = ธนาคารล็อกเงินลูกค้าเอง **ซึ่งทำลายข้ออ้างทางกฎหมายทั้งหมดใน UC-01** (ที่ยืนอยู่บนหลัก "ลูกค้าสมัครใจ") — ต้องเป็นการกดเองเท่านั้น

**เหตุผลที่ไม่รวมดื้อๆ (ตัวเลือก ก เดิม):** ถ้าปล่อยเงินเก่าค้างในกระเป๋ารายวันแล้วเติมรอบใหม่ทับ เป้ารายวันจะคำนวณจากฐานที่ไม่ตรง และ carry-over ข้ามรอบจะทำให้สถิติรอบใหม่เพี้ยนตั้งแต่วันแรก

📊 **metric สำหรับพิช:** อัตราการกด "เก็บเลย" = หลักฐานว่าผู้ใช้อยากออมเมื่อเห็นตัวเลขที่ประหยัดได้จริง

**L2 — นิยาม "ใช้เกินเป้า" ตอนมีเงินสะสม (carry-over)** — ✅ **ตัดสินแล้ว**

**"ใช้เกินเป้า" = ตอนที่ระบบต้องดึง backfill จากบัญชีรายเดือนจริงเท่านั้น** ไม่ใช่การเทียบกับเป้ารายวัน

| สถานการณ์ | นับเป็นใช้เกินไหม |
|---|---|
| เป้า 600 · สะสมมา 900 · วันนี้ใช้ 700 | **ไม่นับ** — ใช้เงินที่ตัวเองประหยัดมา ไม่ได้ดึงจากบัญชีรายเดือน |
| เป้า 600 · ในกระเป๋ามี 100 · ใช้ 450 → ดึง backfill 350 | **นับ 350 บาท** |
| เงินที่ปล่อยจากนิรภัยเข้ามาแล้วใช้จนหมด | **ไม่นับ** — เป็นเงินของผู้ใช้ที่ขอถอนมาเอง (G28) |

**เหตุผล:** นิยามนี้แมปกับ **ledger entry จริง 1 รายการ** (การโอนจากบัญชีรายเดือนนอกรอบ cron) — วัดได้ตรงๆ ไม่ต้องคำนวณเทียบ ไม่มีทางตีความต่างกันระหว่างหน้าจอกับ backend และทำให้ **carry-over มีความหมาย** คนที่ประหยัดไม่โดนตีตราว่าใช้เกิน

**หน้าจอยังแสดง "วันนี้ใช้ไป X จากเป้า Y" ได้** แต่เป็น**ข้อมูล** ไม่ใช่คำเตือน — คำเตือนเด้งเฉพาะตอนเกิด backfill จริง

**L3 — บัญชีรายเดือนหมดก่อนจบรอบ** — ✅ **ตัดสินแล้ว**

เที่ยงคืน cron จะเติมกระเป๋ารายวันแต่บัญชีรายเดือนเหลือ 100 (เป้า 600)

**กฎที่ใช้ — เตือนล่วงหน้า ไม่ใช่รอจนหมด:**

| เงื่อนไข | ระบบทำอะไร |
|---|---|
| บัญชีรายเดือนเหลือ **< 3 เท่าของเป้ารายวัน** | เตือนล่วงหน้า *"เงินรายเดือนเหลือพอใช้อีก 2 วัน — เหลืออีก 8 วันกว่าเงินเดือนจะเข้า"* + เสนอปรับเป้ารายวันลง |
| เที่ยงคืน เงินไม่พอเติมเต็มเป้า | **เติมเท่าที่มี** (ไม่ใช่ไม่เติมเลย) + แจ้งว่าวันนี้ได้เป้าเท่าไหร่ |
| บัญชีรายเดือนเป็น 0 | ไม่เติม + แจ้งชัดว่าเงินรอบนี้หมดแล้ว ห้ามเงียบ ห้าม crash |

**เหตุผล:** เตือนตอนเงินหมดแล้วสายเกินไปสำหรับผู้ใช้ — ต้องเตือนตอนยังเหลือเวลาปรับพฤติกรรม (เกณฑ์ 3 วันมาจากหลักการเดียวกับการกันเงินสำรองใช้จ่ายไว้ในบัญชีหลัก)

### 🟡 รองลงมา

**L4 — auto-approve แต่จำนวนผิดปกติ** — ✅ **ตัดสินแล้ว**

เกณฑ์: เทียบกับ**ค่ากลาง (median) ของ 3 รอบล่าสุด**จากผู้ส่งรายนี้ (ไม่ใช่ค่าเฉลี่ย — median ทนต่อค่าผิดปกติเดี่ยวๆ ได้ดีกว่า เหมือนหลักที่ใช้ใน B3)

| ส่วนต่างจาก median | ระบบทำอะไร |
|---|---|
| อยู่ในช่วง **±30%** | แบ่งอัตโนมัติตามปกติ |
| **เกิน ±30%** (ไม่ว่าน้อยกว่าหรือมากกว่า) | **หยุด auto-approve รอบนี้รอบเดียว** → เด้งถามแบบ UC-02 ปกติ พร้อมข้อความ *"เงินเข้าจากบริษัท ABC ครั้งนี้ 3,000 บาท ต่างจากปกติ (22,500) มาก — ยืนยันแบ่งไหม?"* |
| ผู้ใช้ยืนยันแบ่ง | auto-approve **ยังทำงานต่อในรอบถัดไป** ไม่ถูกยกเลิกถาวร (กันเคสตัดเงินเดือนจริงที่ลดชั่วคราว เช่น ลาไม่รับเงินเต็มเดือน) |

**เหตุผล:** ป้องกันเคสเงินเดือนพลาด/บัญชีถูกแฮกโอนเข้าก้อนเล็กแล้วระบบเผลอ auto-split ก้อนที่ไม่ใช่เงินเดือนจริง โดยไม่ทำให้ผู้ใช้ต้องมายืนยันใหม่ทุกเดือนถ้าเป็นแค่ความผันผวนปกติของเงินเดือน (โบนัส/หักภาษี)

**L5 — เกณฑ์เด้งถาม (threshold)** — ✅ **ตัดสินแล้ว**

"เงินเข้าเกินยอดที่ตั้งไว้" — ยอดนั้น default เท่าไหร่ ถ้าไม่ตั้งแล้วเพื่อนโอน 50 บาทจะเด้งถามไหม

**กฎที่ใช้ 2 ชั้น:**

1. **เกณฑ์ยอด** — เด้งถามเมื่อเงินเข้า ≥ 50% ของรายได้ที่ผู้ใช้กรอกตอน onboarding
2. **กฎเงินผ่านทาง** — เงินก้อนใหญ่ที่ถูกโอนออกเกือบหมดภายใน 24 ชม. **ไม่ใช่รายได้** (เพื่อนโอนมาให้ฝากจ่ายค่าห้อง · เงินกองกลางทริป · ยืมแล้วคืน)
   - ผู้ใช้กด "ไม่ใช่ตอนนี้" → แล้วโอนออก ≥80% ของก้อนนั้นภายใน 24 ชม.
   - → ระบบจำผู้ส่งรายนั้นเป็น **เงินผ่านทาง** ครั้งถัดไปไม่เด้งถาม (แต่ยังเห็นในสถิติ และกดเปลี่ยนกลับได้ในหน้าตั้งค่า)

**เหตุผล:** เกณฑ์ยอดอย่างเดียวไม่พอ — เพื่อนโอน 12,000 ให้ฝากจ่ายค่าห้องผ่านเกณฑ์สบาย ๆ แล้วเด้งถามแบ่งเงินทุกเดือน ผู้ใช้รำคาญจนปิดฟีเจอร์ กฎนี้ใช้กลไก "จำไว้" ตัวเดียวกับ UC-02 แค่จำในทางตรงข้าม

**L6 — ขอถอนนิรภัยเกินยอดที่มี** — ✅ **ตัดสินแล้ว**

**บล็อกตอนกด** — ตรวจ `amount <= nirapai.balance` ที่ server ก่อนสร้าง `WithdrawRequest` ปฏิเสธทันทีถ้าเกิน พร้อมข้อความ *"นิรภัยมีอยู่ 4,500 บาท ขอถอนได้ไม่เกินยอดนี้"*

**เหตุผล:** ยอมให้ "ขอได้แล้วปล่อยเท่าที่มีตอนครบเวลา" สร้างปัญหาซ้อน 2 ชั้น — (1) ผู้ใช้เห็นตัวเลขที่ขอไปตอนกด แต่ได้เงินจริงน้อยกว่าตอนปล่อย ทำให้สับสนว่าเงินหายไปไหน (2) ขัดกับ M10 (server เป็นแหล่งความจริงเดียว, ยอด request ต้องคงที่ตลอด lifecycle ไม่เปลี่ยนตามเหตุการณ์ภายนอกระหว่างทาง) ถ้าอยากถอนเพิ่มเพราะมีเงินเข้าใหม่ ใช้กลไก UC-10 (ขอถอนซ้ำ) แทน

**L7 — เส้นแบ่งวัน** — ✅ **ตัดสินแล้ว → ดู M8 ในหมวดกฎเงินพื้นฐาน**
เก็บ UTC · แสดง Asia/Bangkok · วัน = 00:00:00.000–23:59:59.999 · นับตามเวลาที่ ledger commit ที่ server · cron รัน 00:00 และใช้**วันที่**เป็น idempotency key (รันช้าไม่ทำให้เติมซ้ำหรือข้ามรอบ)

**L8 — โอนเงินเข้านิรภัยเพิ่มระหว่างมีคำขอถอนค้าง** — ✅ **ตัดสินแล้ว**

**ไม่กระทบคำขอเดิมเลย** — `WithdrawRequest` ผูกกับ**จำนวนเงินที่ระบุตอนกด** ไม่ใช่ผูกกับ % หรือยอดคงเหลือของกระเป๋า เงินที่โอนเข้าใหม่:

1. เข้านิรภัยทันทีตามปกติ (ฝากเข้าไม่มี delay — ตามกฎข้อ 1 ของ Logic นิรภัย)
2. **ไม่รวมเข้ากับคำขอที่ pending อยู่** ยอดที่จะปล่อยตอนครบเวลายังเป็นยอดเดิมเป๊ะ
3. หน้านิรภัยแสดงแยกกันชัดเจน: "ยอดทั้งหมด X" กับ "อยู่ระหว่างขอถอน Y (ปลดล็อกวันที่...)"

**เหตุผล:** ผูกสองเหตุการณ์เข้าด้วยกันจะทำให้ตอบยากว่า "ทำไมขอถอน 1,000 แต่ได้ 1,000 เท่าเดิมทั้งที่เพิ่งฝากเพิ่ม 2,000" — แยกกันชัดเจนตรงกับ ledger ที่เก็บเป็นรายการอิสระอยู่แล้ว (M6)

### L9 — เปิดใช้ Pace กลางเดือน (Cold start) — ✅ **ตัดสินแล้ว**

เงินเดือนเข้าไปแล้วตั้งแต่วันที่ 25 · ผู้ใช้มาเปิด Pace วันที่ 10 → ไม่มีเงินเข้าให้ split จนกว่าจะถึงรอบหน้าอีก 15 วัน
**ถ้าไม่ออกแบบ ผู้ใช้ใหม่จะเจอหน้าจอกระเป๋าว่างเปล่าจนกว่าเงินเดือนรอบหน้าจะเข้า = เลิกใช้ไปก่อน**

**กฎที่ใช้ — แบ่งยอดคงเหลือทันที โดยกันบิลที่อ่านเจอจากประวัติไว้ก่อน:**

1. ระบบอ่านบิลจากรายการเดินบัญชีย้อนหลังตั้งแต่ตอน onboarding (UC-01 ข้อ 2) → รู้แล้วว่ามีบิลอะไร ยอดเท่าไหร่ ครบกำหนดวันไหน
2. ถามผู้ใช้ *"ตอนนี้มีเงินในบัญชี 9,400 บาท — กันไว้จ่ายบิลที่เหลือในรอบนี้ 1,400 แล้วแบ่งส่วนที่เหลือ 8,000 เลยไหม?"*
3. กันเฉพาะบิลที่ **ยังไม่ถูกจ่ายและจะครบกำหนดก่อนรอบเงินเข้าถัดไป** (บิลที่จ่ายไปแล้วรอบนี้ไม่กันซ้ำ — ใช้ B4 ตัดสินว่างวดไหนจ่ายแล้ว)
4. คำนวณเป้ารายวันจาก **จำนวนวันที่เหลือจริงถึงรอบเงินเข้าถัดไป** ไม่ใช่ 30 วัน
5. ถ้าประวัติไม่พออ่านบิล → ให้ผู้ใช้กรอกบิลเองผ่าน UC-13 แล้วทำข้อ 2–4 เหมือนเดิม

**เหตุผลที่ทำได้:** การอ่านบิลย้อนหลังไม่ต้องรอเงินเข้ารอบใหม่ — ข้อมูลมีอยู่แล้วในบัญชี ผู้ใช้จึงได้ใช้งานเต็มรูปแบบตั้งแต่นาทีแรก และเห็นคุณค่า ("แอปรู้จักค่าเช่าฉันแล้ว") ก่อนที่จะทันเลิกใช้

**ข้อควรระวัง:** ห้ามกันบิลที่จ่ายไปแล้วซ้ำอีกรอบ — ผู้ใช้จะรู้สึกว่าเงินหายไปเฉย ๆ

### 🔴 L10–L14 — Logic ความน่าเชื่อถือของระบบเงิน — ✅ **ตัดสินแล้วทั้งหมด**

ระบบที่ขยับเงินจริงต้องมีข้อพวกนี้ ไม่มีไม่ได้ — และ Track 1 เป็น track คุณภาพ กรรมการอาจถามตรงๆ

**L10 — Idempotency**

ทุก operation ที่เคลื่อนเงินต้องมี **idempotency key** ที่ฝั่ง server ตรวจก่อนทำงานทุกครั้ง — ถ้า key เคยเห็นมาแล้ว **คืนผลลัพธ์เดิมโดยไม่ทำซ้ำ** (ไม่ error ไม่เงียบ)

| Operation | Idempotency key ประกอบด้วย |
|---|---|
| cron เติมกระเป๋ารายวัน | `user_id + วันที่ (Asia/Bangkok, ตาม M8)` |
| Auto-split จากเงินเข้า | `user_id + transaction_id ของธนาคาร` |
| กดปุ่ม "แบ่งเลย" / "ขอถอน" / "ยกเลิก" จาก client | `client-generated UUID` ที่ client สร้างตอนกดครั้งแรก และส่งซ้ำเหมือนเดิมถ้า retry (ไม่สร้าง UUID ใหม่ตอน retry) |
| backfill ตอนใช้เกิน | `transaction_id ของการจ่ายเงินครั้งนั้น` (backfill ผูกกับธุรกรรมต้นทาง ไม่ใช่เหตุการณ์อิสระ) |
| auto-reserve จาก G12 escalation | `bill_id + due_date` และ recompute ยอดตาม B3 แทนการบวกสะสม |

Key ทุกตัวมี **unique constraint ในฐานข้อมูล** ระดับ table ไม่ใช่แค่เช็คใน application code (กัน race condition ที่ 2 request ตรวจพร้อมกันแล้วเห็นว่ายังไม่มี key ทั้งคู่)

**L11 — ธุรกรรมล้มกลางคัน**

1. ทุกชุดการเคลื่อนเงิน (backfill + หักเงินซื้อ, หรือ split เข้า 3 กระเป๋า) เขียนเป็น **database transaction เดียว** (ตาม M7) — ฐานข้อมูลรับประกัน all-or-nothing เอง ไม่ต้องเขียน compensating logic เอง
2. ถ้า transaction ล้ม (deadlock, connection ขาด) → **retry ทั้งชุดสูงสุด 3 ครั้ง** แบบ exponential backoff (0.5s, 1s, 2s) โดยใช้ idempotency key เดิม (L10) กันซ้ำ
3. ครบ 3 ครั้งยังไม่สำเร็จ → **ปฏิเสธธุรกรรมทั้งหมด** ไม่ใช่ทำครึ่งเดียว แจ้งผู้ใช้ว่า "ทำรายการไม่สำเร็จ ลองใหม่อีกครั้ง" (เงินไม่ขยับเลยสักกระเป๋า — ปลอดภัยกว่าขยับครึ่งเดียว)
4. เขียน log ทุกครั้งที่ retry/ล้ม เพื่อ alert ทีม ops ถ้าเกิดถี่ผิดปกติ

**L12 — Concurrency**

ใช้ **row-level lock แบบ pessimistic** (`SELECT ... FOR UPDATE`) บนแถวกระเป๋าที่จะแก้ไข ไม่ใช้ optimistic versioning เพราะ:
- ธุรกรรมเงินยอมรับการ "รอคิว" ได้ (ผู้ใช้รอ 0.1 วินาทีไม่รู้สึกอะไร) แต่ยอมรับการ "ทำสำเร็จแล้วพบว่าไม่จริง" ไม่ได้
- Optimistic versioning ต้องเขียน retry-on-conflict เองทุกจุด เพิ่มพื้นที่ให้พลาด

**ลำดับการล็อกต้องคงที่เสมอ** (เช่น เรียงตาม `pocket_id`) เพื่อกัน deadlock ตอนธุรกรรมหนึ่งล็อก A→B อีกธุรกรรมล็อก B→A พร้อมกัน

ตัวอย่าง: จ่าย 2 รายการพร้อมกันที่ต้อง backfill จากบัญชีรายเดือนเดียวกัน → รายการที่มาถึงก่อนล็อกแถวได้ก่อน คำนวณว่าดึงได้เท่าไหร่ (ไม่เกิน `balance` ตาม M5) รายการที่สองรอคิวแล้วเห็นยอดที่อัปเดตแล้วจากรายการแรก ไม่มีทางเห็นยอดเก่าพร้อมกันทั้งคู่

**L13 — Undo การแบ่ง**

**ยกเลิกได้ภายใน 15 นาทีหลังกด "แบ่งเลย"** ด้วยเงื่อนไข:

- ระบบสร้างรายการแบ่งเป็นสถานะ `provisional` ก่อน — เงินย้ายจริงตาม ledger ทันที (ผู้ใช้เห็นยอดถูกต้องไม่หน่วง) แต่**เงินที่เข้านิรภัยในช่วง 15 นาทีนี้ยังไม่เริ่มนับ cooldown ที่แสดงกับผู้ใช้ว่า "ล็อกแน่นอนแล้ว"**
- กด "ยกเลิกการแบ่ง" ภายใน 15 นาที → เขียน ledger entry ย้อนกลับทั้งชุด (ตาม M6 — ไม่ลบของเดิม) เงินกลับไปกองที่บัญชีหลักเหมือนก่อนแบ่ง
- เกิน 15 นาที → ยกเลิกไม่ได้อีก เงินในนิรภัยเข้าสถานะ "ล็อกแล้ว" ปกติ ต้องใช้ UC-07 (ขอถอน + cooldown) เท่านั้น

**เหตุผลที่เลือก 15 นาทีไม่ใช่ค่าอื่น:** พอให้ผู้ใช้ทันสังเกตว่ากดผิด (ตัวเลขผิด/เผลอกดบิลของคนอื่น) แต่สั้นพอที่จะไม่กลายเป็น escape hatch เลี่ยง cooldown จริง — ยาวกว่านี้เริ่มเสี่ยงเป็นช่องโหว่ A+2 (ธนาคารต้องพิสูจน์ว่าไม่ใช่การหน่วงเงินปลอม)

**L14 — หลาย device**

ผูกกับ L12 โดยตรง — **ไม่มี logic แยกสำหรับ multi-device** เพราะ row lock ที่ระดับฐานข้อมูล (L12) ทำงานไม่สนใจว่า request มาจาก device ไหน กดขอถอนพร้อมกัน 2 เครื่อง = 2 request ที่แข่งกันล็อกแถวเดียวกัน คำขอที่มาถึงก่อนได้ประมวลผลก่อนตาม L12 คำขอที่สองรอแล้วเห็นสถานะที่อัปเดตแล้ว (มี pending request อยู่แล้ว) → เข้ากลไก UC-10 (รวมเป็นคำขอเดียว) โดยอัตโนมัติ ไม่สร้างสองรายการ

| **G03** 🟡 | **ผู้ใช้มีหลายบัญชีใน K PLUS** — Pace ผูกกับบัญชีไหน เงินเข้าอีกบัญชีนับไหม | PoC รองรับบัญชีหลักเดียวที่ผู้ใช้เลือกตอน onboarding · ระบุเป็นข้อจำกัด |

### UC-01 — Onboarding

| **G06** 🔴 | **cooldown ตั้งได้ช่วงไหน** — เอกสารบอกแค่ "เช่น 24 ชม." ไม่มีขั้นต่ำ/สูงสุด ตั้ง 1 นาทีได้ = ฟีเจอร์ไร้ความหมาย · ตั้ง 1 ปีได้ = อันตรายและอาจขัดกฎ | กำหนดช่วง **12–72 ชม.** (default 24) — มีขอบเขตชัด อธิบายได้ และยังอยู่ในกรอบที่เทียบกับฝากประจำได้ |
| **G07** 🟡 | **ตั้งนิรภัยเป็น 0% ได้ไหม** — ผู้ใช้ที่ไม่อยากออมเลย | ได้ และถ้า 0% ก็**ไม่ต้องเปิดบัญชีนิรภัย** (ใช้ 2 กระเป๋า) — เปิดทีหลังได้ แต่ตอนเปิดต้องตั้ง cooldown ใหม่ตามกฎเดิม |
| **G08** 🟡 | **ปิดแอปกลางคัน onboarding** — สร้างกระเป๋าไปแล้ว 2 จาก 3 | สร้างทุกอย่างเป็น transaction เดียวตอนกดยืนยันครั้งสุดท้ายเท่านั้น · ระหว่างทางเก็บเป็น draft ไม่แตะเงินจริง |
| **G09** 🟡 | **สร้าง ePocket ไม่สำเร็จ** (ระบบธนาคารล่ม) | rollback ทั้งชุด + แจ้งผู้ใช้ให้ลองใหม่ ห้ามค้างสถานะครึ่ง (ผูกกับ G08) |
| **G10** 🟡 | **เปิดใช้ Pace ซ้ำหลังเคยปิด** — บิลเดิม/ผู้ส่งที่จำไว้/สถิติเก่า ยังอยู่ไหม | ถามผู้ใช้ว่าจะใช้ค่าเดิมหรือเริ่มใหม่ · ถ้าเลยระยะเก็บข้อมูลตาม S8 แล้วก็เริ่มใหม่อย่างเดียว |
| **G11** 🟡 | **ฟรีแลนซ์กรอก "รายได้ประมาณ" ไม่ได้** แต่ค่านี้เป็นฐานของเกณฑ์เด้งถาม L5 (50%) | ให้กรอกเป็นช่วง (ต่ำสุด–สูงสุด) แล้วใช้ **ค่าต่ำสุด** เป็นฐานคำนวณ 50% |

### UC-02 / UC-03 — เงินเข้า + แบ่ง

| # | ช่องโหว่ | ข้อเสนอ |
|---|---|---|
| **G12** 🔴 | **ผู้ใช้ไม่ตอบ dialog เลย** — ต้องแยกระหว่าง pending item ที่มี deadline ของบิล กับเงินเข้าทั่วไปที่ไม่มี deadline | ถ้า pending item ผูกกับบิลและมี `due_date` จริง: เริ่ม escalation เมื่อ `today >= due_date - ESCALATION_LEAD_DAYS` โดยค่าเริ่มต้น 5 วัน → เตือนวันละครั้งสูงสุด 3 ครั้ง → ยังไม่ตอบให้**กันเงินบิลไว้ก่อนโดยอัตโนมัติ** แต่**ไม่แบ่งเข้ากระเป๋า**จนกว่าผู้ใช้จะยืนยัน. ถ้า `due_date == null`: อยู่ใน passive queue ตาม H2.3 และไม่มี reminder อัตโนมัติ |
| **G13** 🔴 | **กด "ไม่ใช่ตอนนี้" แล้วเปลี่ยนใจ** — pending income อาจค้างข้ามรอบได้ และไม่ควรถูกปิดหน้าต่างโดยไม่มีการแจ้ง | เก็บเป็นรายการ "เงินเข้าที่ยังไม่ได้แบ่ง" โดยไม่ผูกกับ `cycle_id` และไม่มีวันหมดอายุ; ผู้ใช้กดจัดการเองได้ทุกเมื่อ; `pending_unsplit` ต้องถูกหักออกจาก `available` จนกว่าจะจัดการสำเร็จ |
| **G14** 🔴 | **เงินเข้าถูกตีกลับหลังแบ่งไปแล้ว** — โอนผิดแล้วธนาคารดึงคืน แต่ 20% เข้านิรภัยติด cooldown ไปแล้ว **บังคับเกิด ไม่ใช่ผู้ใช้เลือก** ต่างจาก L13 ที่เป็นการกดผิดเอง | ต้องมีเส้นทาง **บังคับย้อนการแบ่ง** ที่ดึงเงินคืนจากทุกกระเป๋ารวมถึงนิรภัยได้ทันทีโดยไม่ต้องรอ cooldown (เพราะเงินนั้นไม่ใช่ของผู้ใช้ตั้งแต่แรก) — เขียนเป็น operation แยกที่มี audit log ชัด |
| **G15** 🔴 | **บิลไหนกันก่อนเมื่อเงินไม่พอ** — edge case เขียนว่า "กันให้ได้มากที่สุด" แต่ไม่บอกลำดับ | เรียงตาม **วันครบกำหนดที่ใกล้ที่สุดก่อน** (บิลที่จะเด้งก่อนได้เงินก่อน) ไม่ใช่เรียงตามยอด |
| **G16** 🔴 | **"บิลที่ครบกำหนดก่อนรอบเงินเข้าถัดไป" คำนวณไม่ได้สำหรับฟรีแลนซ์** — ไม่มีรอบถัดไปให้อ้างอิง | ฟรีแลนซ์ใช้ **"บิลที่ครบกำหนดภายใน N วันข้างหน้า"** โดย N = จำนวนวันที่ผู้ใช้ตอบใน UC-03 ข้อ 5 ("ก้อนนี้ต้องใช้กี่วัน") |
| **G17** 🟡 | **เงินเข้าหลายก้อนในวันเดียว** (เงินเดือน + โบนัส) หรือก้อนใหม่เข้าตอน dialog เก่ายังค้าง | ต่อคิวทีละก้อน ไม่ซ้อน dialog · แต่ละก้อนแบ่งแยกกัน ไม่รวมยอด |
| **G18** 🟡 | **ผู้ใช้แก้ % ระหว่าง dialog ค้างอยู่** | ใช้ % ณ ตอนที่**กดยืนยัน** ไม่ใช่ตอนที่ dialog เด้ง + แสดงยอดใหม่ให้เห็นก่อนกด |
| **G19** 🟡 | **ฟรีแลนซ์: ก้อนใหม่เข้าก่อนก้อนเก่าหมดอายุ** — ตอบว่าใช้ 30 วัน แต่งวดใหม่มาวันที่ 12 เกิดถี่กว่า L1 ของพนักงานประจำมาก | ผูกกับการตัดสิน L1 — ไม่ว่าเลือกทางไหน **ต้องใช้กฎเดียวกันทั้งสอง persona** |

## 🔔 กฎการแจ้งเตือน — กัน Alert Fatigue (ใช้ร่วมทุก UC)

Pace เติมเงินทุกเที่ยงคืน + เตือนทุกครั้งที่ใช้เกินเป้า = มีโอกาสเตือนผู้ใช้วันละหลายครั้ง **ถ้าเตือนพร่ำเพรื่อ ผู้ใช้จะปิดการแจ้งเตือนทั้งหมด แล้วเตือนตอนสำคัญจริงก็ไม่มีใครเห็น** (งานวิจัยเรื่อง warning habituation ชี้ตรงกันว่าคนเลิกอ่านคำเตือนที่เห็นซ้ำๆ)

### กฎ

| เหตุการณ์ | ระดับการแจ้ง | เหตุผล |
|---|---|---|
| เติมกระเป๋ารายวันตอนเที่ยงคืน (ปกติ) | **ไม่เด้งเตือน** — อัปเดตยอดบนหน้าหลักเงียบๆ | เกิดทุกวัน ไม่ใช่เรื่องที่ต้องรู้ทันที |
| แบ่งเงินอัตโนมัติรอบถัดไป (ติ๊ก "จำไว้" แล้ว) | **แจ้งครั้งเดียวแบบสรุป** ไม่ขัดจังหวะ กดดูรายละเอียดได้ | ผู้ใช้อนุญาตไว้แล้ว แต่ต้องรู้ว่าเกิดขึ้น |
| ใช้เกินเป้ารายวันครั้งแรกของวัน | **เด้ง warning 1 ครั้ง** + ตัวเลข "เกินเป้าไปแล้ว X บาท" ค้างบนหน้ากระเป๋าตลอดวัน | ครั้งแรกคือข้อมูลใหม่ ควรรู้ |
| ใช้เกินเป้าครั้งที่ 2, 3, 4… ของวันเดียวกัน | **ไม่เด้งซ้ำ** — อัปเดตแค่ตัวเลขที่ค้างอยู่ | เด้งทุกครั้งที่จ่ายเงิน = รำคาญจนปิดฟีเจอร์ |
| บัญชีรายเดือนใกล้หมด (เหลือไม่ถึง ~3 วันของเป้า) | **เด้ง 1 ครั้ง** | เรื่องสำคัญจริง ต้องรู้ก่อนเงินหมด |
| ขอถอนนิรภัย / ก่อนปล่อยเงิน ~1 ชม. / ปล่อยเงินแล้ว | **เด้งทุกครั้ง ห้ามตัด** | เป็นการเคลื่อนเงินก้อนออม ผู้ใช้ต้องรู้ทุกจุด (ดู UC-07, UC-08) |
| โอนเงินเข้านิรภัยเพิ่มเอง | **ไม่เตือน** แค่ receipt | ผู้ใช้ทำเอง และเป็นทิศทางที่ดีอยู่แล้ว |

### หลักที่ใช้ตัดสินเวลามีเคสใหม่

1. **เตือนเมื่อเงินเคลื่อนออกจากที่ที่ผู้ใช้ตั้งใจเก็บไว้ ไม่ใช่เตือนทุกครั้งที่ระบบทำงาน**
2. **เหตุการณ์เดิมในวันเดียวกันเตือนครั้งเดียว** ที่เหลือใช้ตัวเลขค้างบนหน้าจอแทน
3. **ห้ามใช้สีเป็นสัญญาณเดียว** — ต้องมีข้อความบอกด้วยเสมอ (คนตาบอดสีและคนที่อ่านผ่านๆ)
4. **ห้ามใช้ถ้อยคำกล่าวโทษผู้ใช้** — "วันนี้ใช้เกินเป้าไป 350 บาท" ไม่ใช่ "คุณใช้เงินเกินตัว"
5. ต้องวัดในการทดสอบผู้ใช้ว่ามีสัญญาณ alert fatigue ไหม (กดปิดโดยไม่อ่าน / บอกว่าจะปิดฟีเจอร์)

## 🔐 ข้อกำหนดด้านความปลอดภัยและ PDPA (ใช้ร่วมทุก UC)

Pace เก็บเงินเดือน รายการบิล และพฤติกรรมใช้จ่าย = ข้อมูลส่วนบุคคลเต็มตัว ข้อพวกนี้เป็น **ข้อกำหนดการ implement** ที่ต้องมี test case รองรับ ไม่ใช่จุดขายที่เอาไปพิช

| # | ข้อกำหนด | ทดสอบยังไง |
|---|---|---|
| **S1** | **เก็บเท่าที่จำเป็น** — ยอดเงิน วันที่ รหัสผู้ส่ง/ผู้รับ รายการบิล · **ห้ามอ่าน SMS / อีเมล / clipboard** | ตรวจ schema ว่าไม่มีฟิลด์ที่ไม่ได้ใช้ · ตรวจว่าแอปไม่ขอ permission อ่านข้อความ |

| **S3** | **ผู้ใช้ดูได้ว่าระบบใช้ข้อมูลอะไร** และปิดได้ | มีหน้าจอนี้ในแอป |
| **S4** | **Cooldown คิดที่ server เท่านั้น** (ย้ำจาก UC-07) | ปรับนาฬิกาเครื่อง / ยิง API ตรง แล้วปล่อยเงินก่อนกำหนดไม่ได้ |
| **S5** | **Auth เข้มขึ้นตอนแก้กฎเงิน** — แก้ % split, แก้เป้ารายวัน, ขอถอนนิรภัย ต้องยืนยันตัวตนเพิ่ม | เทสว่าข้ามขั้นยืนยันแล้วทำไม่ได้ |

| **S7** | **กุญแจเข้ารหัสอยู่ใน keystore ไม่ฝังในโค้ด** · least-privilege + audit log | code review + ตรวจว่าไม่มี secret ใน repo |
| **S8** | **กำหนดระยะเวลาเก็บข้อมูลและการลบ** ให้ชัด | มีเอกสารระบุ ไม่ใช่เก็บไว้ตลอดไปโดยไม่มีเหตุผล |

## หน้าจอที่ต้องทำ (PoC)
