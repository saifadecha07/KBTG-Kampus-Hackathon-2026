### ตัดสินใจที่ปิดแล้ว
- [x] **สูตรเป้ารายวัน** — ระบบคำนวณแนะนำ → ผู้ใช้กดรับหรือแก้เอง → ล็อกคงที่ทั้งรอบ
- [x] **แยกเงินเดือน/ฟรีแลนซ์ยังไง** — ไม่เดา ให้ยืนยันตอนเงินเข้า + จำผู้ส่งไว้ทำอัตโนมัติรอบหน้า
- [x] **บิลอัตโนมัติจะเด้งไหม** — เช็ครายการหักอัตโนมัติแล้วกันเงินไว้ในบัญชีหลัก ไม่กวาด
- [x] **กฎหมายให้ล็อกเงินไหม** — ทำเป็นประเภทบัญชีที่ลูกค้าสมัครใจเปิด ตั้ง cooldown ครั้งเดียวแก้ไม่ได้ (หลักเดียวกับฝากประจำ)
- [x] **หนี cooldown ด้วยการปิดฟีเจอร์ได้ไหม** — ไม่ได้ ปิดบัญชีนิรภัยเงินก็ยังต้องรอ
- [x] **จ่ายเกินวงเงินรายวันแล้วบล็อกไหม** — ไม่บล็อก ดึงชดเชยจากบัญชีรายเดือน + เตือน + เก็บสถิติ
- [x] **ระบบรู้ได้ยังไงว่าอันไหนคือบิล** — กฎ B1–B4 ใน `design_usecase.md` (ผู้รับเดิม ≥3 รอบ · ยอด ≥300 · วันที่ในเดือนห่างไม่เกิน 7 · เดือนละครั้ง) **ใช้วันที่ในเดือน ไม่ใช่ระยะห่างเป็นวัน**
- [x] **กันเงินบิลเท่าไหร่** — บิลคงที่ (แกว่ง <15%) กัน `max(ยอดล่าสุด, ยอดกลาง)` · บิลผันผวน กัน percentile 75
- [x] **บิลเลิกใช้แล้วทำยังไง** — สถานะ `active` → `late` → `stopped` พอ `stopped` คืนเงินที่กันไว้เข้าบัญชีรายเดือน
- [x] **บิลที่ระบบมองไม่เห็น** — ยอมรับเป็นข้อจำกัด (บิลผูกบัตร · บิลใหม่ยังไม่ครบ 3 รอบ · บิลรายปี) แล้วอุดด้วย UC-13 ให้ผู้ใช้เพิ่มเอง
- [x] **L3 บัญชีรายเดือนหมดก่อนจบรอบ** — เตือนตั้งแต่เหลือ <3 เท่าของเป้ารายวัน · เที่ยงคืนเงินไม่พอ เติมเท่าที่มี · เงิน 0 แจ้งชัด ไม่ crash
- [x] **L5 เกณฑ์เด้งถาม** — เงินเข้า ≥50% ของรายได้ + กฎเงินผ่านทาง (ก้อนใหญ่ที่โอนออก ≥80% ใน 24 ชม. = ไม่ใช่รายได้ จำผู้ส่งไว้ไม่เด้งซ้ำ)
- [x] **L9 cold start** — อ่านบิลจากประวัติตั้งแต่ onboarding แล้วแบ่งยอดคงเหลือทันที เป้ารายวันคิดจากวันที่เหลือจริง **ห้ามกันบิลที่จ่ายไปแล้วซ้ำ**
- [x] **A+3/B2 incentive** — ดอกเบี้ยพิเศษกระเป๋านิรภัย **เพดาน 50,000 บาทแรก** (≈ เงินสำรอง 2–3 เดือนของกลุ่มเป้าหมาย ธนาคารคุมต้นทุนได้ precedent คือ MAKE) · สำรอง = K Point · **ต้องติดป้ายว่าขึ้นกับ Business approval**
- [x] **B3 security/privacy** — เขียนเช็คลิสต์ PDPA S1–S8 ใน `design_usecase.md` + สรุปในแผนทดสอบ `pace_strategy.md`
- [x] **กฎกัน alert fatigue** — เติมเงินรอบปกติไม่เด้ง · ใช้เกินเป้าเด้งครั้งแรกของวันครั้งเดียว · การเคลื่อนเงินนิรภัยเด้งครบทุกจุด
- [x] **แผน usability test เต็มรูปแบบ** — task T1–T5 · rubric · severity · เกณฑ์ตัดสิน continue/revise/pivot · **ต้อง pilot 1 คนก่อนรัน 5–8 คน**
- [x] **กฎเงินพื้นฐาน M1–M12** — integer สตางค์ห้าม float · ปัดลงแล้วเศษเข้าบัญชีรายเดือน · เป้ารายวันปัดลงเป็นบาทเต็ม · **invariant ผลรวมต้องตรงเสมอ** · ห้ามกระเป๋าติดลบ · ledger 2 ขาเขียนอย่างเดียว · transaction เดียวต่อชุด · **ปิด L7** (UTC เก็บ / Asia/Bangkok แสดง / นับตามเวลา commit) · **แยก `reserved` ออกจาก `balance`** · server เป็นแหล่งความจริงเดียว
- [x] **ไล่ตรวจทุก UC หาช่องโหว่ที่ยังไม่เคยลิสต์ — เจอ 49 ข้อ (G01–G49)** พร้อมข้อเสนอทุกข้อ

### ✅ ปิดหมดแล้ว (12 ก.ย. 2026) — logic ครบก่อนเข้า architecture

- [x] **L1** จบรอบ → กวาดกระเป๋ารายวันคืนบัญชีรายเดือนก่อนแบ่งใหม่ · เสนอ "เก็บเลย/ใช้ต่อ" ไม่บังคับโยกนิรภัย
- [x] **L2** "ใช้เกินเป้า" = เกิด backfill จริงเท่านั้น ไม่ใช่เทียบเป้ารายวันเฉยๆ
- [x] **L4** auto-approve ต่างจาก median 3 รอบล่าสุด >±30% → เด้งถามใหม่
- [x] **L6** ขอถอนเกินยอดนิรภัย → บล็อกตอนกด
- [x] **L8** ฝากเข้านิรภัยระหว่างมี request pending → ไม่กระทบยอด request เดิม
- [x] **L10–L14** idempotency key + unique constraint · retry 3 ครั้งแล้ว rollback ทั้งชุด · row lock ลำดับคงที่กัน deadlock · ยกเลิกแบ่งได้ 15 นาที · multi-device ผ่านกลไกเดียวกับ L12
- [x] **A7 / A8 / A+5** merge-timer (ลดยอดไม่รีเซ็ตเวลา) · เงินเดือนรอบสองต่อคิวไม่ re-split · refund เข้ากระเป๋ารายวัน + หักสถิติคืน
- [x] **G-series ทั้ง 49 ข้อ** — ทุกข้อมีกฎที่ใช้จริงแล้ว ดู `design_usecase.md` หมวด G

- [ ] Unit — split รวม 100% · เศษสตางค์เข้าบัญชีรายเดือน (M2) · เป้ารายวันปัดลง (M3) · top-up ส่วนต่าง · carry-over
- [ ] **Property test — invariant (M4)** — สุ่มธุรกรรม 10,000 รายการแล้วผลรวมทุกกระเป๋าต้องตรงทุกครั้ง *(หลักฐานคุณภาพชิ้นที่แข็งแรงที่สุดสำหรับพิช)*
