## 1. ไอเดีย: Pace

**Concept:** เงินเดือนเข้า → ระบบ auto-split เข้า ePocket 3 บัญชี (เงินรายเดือน / ใช้จ่ายรายวัน / นิรภัย) ให้อัตโนมัติ ไม่ต้องโยกเงินเอง กระเป๋าใช้จ่ายรายวันถูกเติมให้ทุกวันจากบัญชีเงินรายเดือนตามเป้าที่ตั้งไว้ ส่วนกระเป๋านิรภัยถอนออกไม่ได้ทันที ต้องรอ cooldown ก่อน

### 3 กลไก (ePocket ทั้งหมด 3 บัญชี: เงินรายเดือน / ใช้จ่ายรายวัน / นิรภัย)

1. **Auto-Split ตอนเงินเข้า** — rule engine โอนแยกเข้าแต่ละ ePocket ตามสัดส่วนที่ตั้งไว้ล่วงหน้า (**บัญชีเงินรายเดือน** เก็บก้อนหลักไว้ / **บัญชีนิรภัย** ได้ส่วนออม/ฉุกเฉินทันที) แทนที่ผู้ใช้ต้องโยกเงินเองแบบ ePocket ปกติ
   - **Trigger = ยืนยัน ไม่ใช่เดา (ตัดสินใจแล้ว)** — ระบบ**ไม่เดา**ว่าเงินก้อนไหนคือเงินเดือน เพราะเดาผิดแล้วแบ่งเงินที่เพื่อนโอนคืนหรือเงินคืนภาษีจะกวนใจมาก แทนที่จะเดา: เงินเข้าเกินยอดที่ผู้ใช้ตั้งไว้ → **เด้งถาม "แบ่งเงินก้อนนี้ตามแผนไหม?"** → ผู้ใช้กดยืนยันครั้งเดียว split ทำงานทันที + มีตัวเลือก **"จำไว้ ทำอัตโนมัติทุกครั้งจากผู้ส่งรายนี้"** สำหรับคนเงินเดือนประจำ (หลังกดครั้งแรก ครั้งต่อไปอัตโนมัติเต็มรูปแบบ)
   - **ฟรีแลนซ์/รายได้ไม่ประจำใช้ได้ด้วยกลไกเดียวกัน** — เงินเข้าไม่ตรงงวด จำนวนไม่เท่ากัน ก็แค่กดยืนยันตอนเงินเข้า ไม่ต้องเขียน logic แยกสองระบบ ไม่ต้องมี ML ทายรายได้ — **จุดนี้พิชได้ว่าครอบคลุม first jobber ที่เป็นฟรีแลนซ์/มีงานเสริมด้วย** ไม่ใช่เฉพาะพนักงานประจำ
2. **Daily Auto-Refill กระเป๋าใช้จ่ายรายวัน** (ดูรายละเอียด logic ด้านล่าง)
3. **กระเป๋านิรภัย (Vault) แบบหน่วงเวลา** — เงินออม/ฉุกเฉินถูกโยกเข้าอัตโนมัติ ถอนออกไม่ได้ทันที ต้องรอ cooldown (เช่น 24–48 ชม.) — ชั้นหน่วงนี้คือของจริงที่ **ePocket ปกติไม่มี** (ePocket ถอนได้ทันทีเหมือนออมทรัพย์ทั่วไป) **ฟีเจอร์นี้คือ "หน่วงเพื่อการออม" ล้วนๆ ไม่ใช่ระบบตรวจจับ/ป้องกัน scam โดยตรง** ประโยชน์ที่ได้เป็นผลทางอ้อม 3 อย่าง: (1) มีเวลาคิดตัดสินใจนานขึ้นก่อนเงินออกจากนิรภัยจริง (2) เห็น/ทบทวนพฤติกรรมใช้เงินตัวเองชัดขึ้นจากการต้องมากดขอถอนแทนที่จะหยิบใช้ได้ทันที (3) เวลาคิดที่มากขึ้นนี้ **อาจ**ช่วยลดโอกาสโดน scam ได้บ้างเป็นผลพลอยได้ — ไม่ใช่การรับประกันว่ากันโกงได้
   - **กติกาหน่วงผูกกับ "ประเภทบัญชี" ไม่ใช่ "จำนวนเงิน"** — ถอนจากนิรภัยแล้วต้องรอ cooldown เสมอ ไม่ว่าจะถอน 1,000 บาทหรือหลักหมื่น (เพราะเป็นบัญชีออม ไม่ใช่บัญชีใช้จ่าย) ต่างจากมาตรการ ธปท./risk scoring ทั่วไปที่หน่วงเฉพาะธุรกรรมจำนวนมาก/ผิดปกติเท่านั้น — ทำให้เป็นกฎที่ตรงไปตรงมา เข้าใจง่าย และเทสง่ายกว่า (ไม่ต้องมี risk engine)

### 📱 User Flow (ใช้เป็นสคริปต์ demo ได้เลย)

**เคส 1 — พนักงานประจำ (พลอย เงินเดือน 22,500 เข้าทุกวันที่ 25)**

1. เงิน 22,500 เข้าบัญชี → K PLUS เด้ง: *"เงินเข้า 22,500 บาท — แบ่งตามแผน Pace ไหม?"* `[แบ่งเลย] [ไม่ใช่ตอนนี้]` + checkbox *"จำไว้ ทำอัตโนมัติทุกครั้งจากผู้ส่งนี้ (บริษัท ABC)"*
2. กด **แบ่งเลย** + ติ๊กจำไว้ → split ทันที: **นิรภัย 4,500** (ล็อก รอ cooldown ถ้าจะถอน) / **บัญชีรายเดือน 18,000**
3. ระบบคำนวณต่อ: 18,000 ÷ 30 วัน → *"แนะนำ **600 บาท/วัน**"* `[ใช้ตัวนี้] [แก้เอง]`
4. กดรับ → ล็อกค่าทั้งรอบ → เที่ยงคืนทุกวันกระเป๋ารายวันถูกเติมให้ถึง 600 จากบัญชีรายเดือน
5. **เดือนถัดไปไม่เด้งถามอีก** เพราะติ๊กจำไว้แล้ว → อัตโนมัติเต็มรูปแบบ

**เคส 2 — ฟรีแลนซ์ (น้ำ ลูกค้าโอนไม่ตรงงวด จำนวนไม่เท่ากัน)**

1. ลูกค้าโอน 15,000 วันไหนก็ได้ → เด้งถามแบบเดียวกัน
2. กดแบ่งเลย แต่ **ไม่ติ๊กจำไว้** (ลูกค้าคนละเจ้าทุกครั้ง) → split ทำงานเหมือนกันเป๊ะ
3. ถามว่าก้อนนี้ต้องใช้กี่วัน (เช่น 30) → แนะนำ 400 บาท/วัน
4. งวดหน้าเงินเข้าอีก กดยืนยันใหม่

> **หัวใจ:** ระบบไม่เดาว่าเงินก้อนไหนคือรายได้ → ให้กดยืนยันครั้งเดียว แก้ 2 ปัญหาพร้อมกัน: ไม่เผลอแบ่งเงินที่เพื่อนโอนคืน/เงินคืนภาษี **และ** ฟรีแลนซ์ใช้โค้ดชุดเดียวกันได้ ไม่ต้องมี ML ไม่ต้องแยกสองระบบ

### Logic การเติมเงินของกระเป๋าใช้จ่ายรายวัน (ละเอียด)

1. **ตั้งเป้าหมายรายวัน — ระบบคำนวณแนะนำให้ ผู้ใช้แก้เองได้ (ตัดสินใจแล้ว)** — ตอนเงินเข้าและยืนยัน split ระบบคำนวณยอดแนะนำให้ (ยอดบัญชีเงินรายเดือน ÷ จำนวนวันจนถึงรอบเงินเข้าถัดไป เช่น 8,400 ÷ 30 = 280 บาท/วัน) แล้ว**เสนอเป็นค่าแนะนำ** ผู้ใช้กดรับหรือพิมพ์ตัวเลขเองก็ได้ → พอยืนยันแล้วยอดนี้ **คงที่ทั้งรอบ** (ไม่คำนวณใหม่ทุกวันให้สับสน) — ได้ข้อดีทั้งสองแบบ: ฉลาดพอที่ไม่ต้องคิดเอง แต่ยังคุมได้เอง และเทสง่ายเพราะค่าคงที่
2. **Top-up รายวัน (cron job เที่ยงคืน)** — เช็คยอดคงเหลือในบัญชีใช้จ่ายรายวัน ถ้าน้อยกว่าเป้าหมาย → หักส่วนต่างจาก **บัญชีเงินรายเดือน** มาเติมให้ครบเป้าหมายพอดี (เติมแค่ส่วนต่าง ไม่ใช่เติมเต็มจำนวนใหม่ทุกวัน) → เงินที่ใช้ไม่หมดจากเมื่อวานสะสมต่อได้ (carry-over)
3. **ใช้เกินเป้าหมายได้ (ไม่บล็อก) — เติมแล้วจ่ายจากกระเป๋ารายวันเสมอ ไม่สลับไปหักบัญชีรายเดือนตรงๆ** — ก่อนตัดเงินซื้อ ระบบเช็คว่ายอดกระเป๋ารายวันพอไหม ถ้าไม่พอ → ดึงส่วนที่ขาดจากบัญชีเงินรายเดือนมา**เติมกระเป๋ารายวันก่อน** (real-time, เป็น atomic operation เดียวกับการตัดเงินซื้อ) แล้วค่อยตัดเงินซื้อจากกระเป๋ารายวันตามปกติ — ธุรกรรมในสายตาผู้ใช้จึงมาจาก **กระเป๋ารายวันเสมอ** ไม่มีการสลับไปหักบัญชีรายเดือนโดยตรง (เหตุผล: ช่องทางชำระผูกกับบัญชีเดียวอยู่แล้วสลับกลางธุรกรรมไม่ได้จริง + ทำให้นับสถิติ "ใช้เกินกี่บาทกี่วัน" ง่ายเพราะทุกธุรกรรมนับที่กระเป๋าเดียว)
4. **Warning + เก็บสถิติ + โชว์ยอดเกินของวันนี้แบบ real-time** — ทุกครั้งที่ใช้เกินเป้าหมายรายวัน ขึ้น warning แจ้งผู้ใช้ทันที + บันทึกสถิติสะสม (ใช้เกินไปกี่บาท, เกินมากี่วันในเดือนนี้) — **warning ต้องโชว์ยอดคงเหลือบัญชีเงินรายเดือนหลังหักด้วย** ไม่ใช่บอกแค่ "ใช้เกินไป X บาท" เฉยๆ เพราะการดึงเงินจากรายเดือนมาชดเชยกระทบเงินสำรองส่วนอื่น (เช่นเงินที่กันไว้จ่ายบิลปลายเดือน) — นอกจาก warning ที่เด้งแล้วหาย หน้ากระเป๋ารายวันของ**วันนั้น**ต้องโชว์ตัวเลข "เกินเป้าไปแล้ว X บาท" ค้างอยู่ตลอดวัน (ไม่ใช่แค่เด้งเตือนแวบเดียว) ให้เห็นสดๆ ตลอดว่าวันนี้เกินไปเท่าไหร่ ตัวเลขนี้รีเซ็ตทุกเที่ยงคืนพร้อมรอบ top-up ใหม่ — ยอดบัญชีเงินรายเดือนควรอยู่บนหน้าหลักคู่กับกระเป๋ารายวันตลอดเวลา ไม่ใช่ซ่อนไว้

*(ธุรกรรมจะถูกปฏิเสธก็ต่อเมื่อบัญชีเงินรายเดือนหมดจริงเท่านั้น — เงินหมดก็คือหมด ไม่ใช่ logic พิเศษ แค่ทดสอบไว้กันระบบ crash/เงียบตอนเจอเคสนี้)*

### Logic การหน่วงเงินของกระเป๋านิรภัย (ละเอียด)

1. **ฝากเข้า** — ไม่ว่าจาก auto-split หรือผู้ใช้โยกเงินเพิ่มเอง เข้าได้ทันที ไม่มี delay (delay มีผลแค่ตอน**ถอนออก**เท่านั้น)
2. **ขอถอน** — ผู้ใช้กดขอถอนจำนวนเท่าไหร่ก็ได้ (ไม่มีขั้นต่ำ/สูงสุด) → ระบบสร้าง "คำขอถอน" สถานะ pending พร้อมเริ่มจับเวลา cooldown (default เช่น 24 ชม. ปรับได้)
3. **ระหว่างรอ** — เงินยังอยู่ในนิรภัยเหมือนเดิม (ยังไม่ตัดออกจนกว่าจะครบเวลา) มี notification 2 จุด: (ก) ทันทีที่กดขอถอน ให้รู้ตัวว่าเพิ่งกดอะไรไป (ข) ก่อนครบกำหนดปล่อยเงินจริง ~1 ชม. เป็นโอกาสสุดท้ายให้เปลี่ยนใจ
4. **ยกเลิกได้ตลอดช่วง cooldown** — กดยกเลิกคำขอเมื่อไหร่ก็ได้ก่อนครบเวลา → เงินอยู่ในนิรภัยต่อ ไม่มีบทลงโทษ/ค่าปรับ
5. **ครบเวลา cooldown** — ระบบย้ายเงินจากนิรภัยเข้ากระเป๋าใช้จ่ายให้อัตโนมัติ (ไม่ต้องกดยืนยันซ้ำ กันลืมแล้วเข้าใจว่าเงินหาย)
6. **ขอถอนซ้ำระหว่างมีคำขอ pending อยู่แล้ว** — รวมเป็นคำขอเดียว นับเวลา cooldown ใหม่จากคำขอล่าสุด (กันช่องโหว่ถอนทีละน้อยๆ ถี่ๆ เพื่อเลี่ยง delay)

*ตัด "ยืมจากอนาคตตัวเอง" ออกแล้ว — feedback ว่า logic แปลก เข้าใจยาก*

### ⚠️ มุมที่ใช้พิชแต่ละกลไก (สำคัญ — อ่านก่อนพิช)
ทั้ง 3 กลไกยังเป็นแกนหลักเท่ากัน แค่ "มุมที่ใช้พิช" ต้องเลือกให้ถูก:
- **Auto-Split** → **แก้แล้ว: ไม่ใช่ "ของใหม่ที่ไม่มีใครทำ" อีกต่อไป** (Qapital "Payday Divvy" ทำมาก่อนหลายปี — ดู section 3) พิชเป็น **"ไม่มีธนาคารไทยไหนทำ + ผูกกับ ePocket เดิม"** แทน (regional + integration novelty ไม่ใช่ global novelty)
- **Daily Auto-Refill** → พิชเป็น "ระบบช่วยเห็นพฤติกรรมใช้เงินตัวเอง" (ใช้เกินได้ไม่บล็อก แต่มี warning + สถิติสะสมให้เห็นภาพรวม) ไม่ใช่พิชว่า "มีเพดานบังคับใช้จ่ายรายวัน" เพราะจริงๆ ไม่บังคับ พูดเกินจะโดนจับผิดง่าย — **จุดเด่นที่ควรเน้น:** กลไก auto top-up ข้ามกระเป๋าแบบ atomic (เติมกระเป๋ารายวันจากบัญชีรายเดือนก่อนตัดเงินซื้อ + โชว์ผลกระทบยอดรายเดือน real-time) เป็นดีเทลที่ธนาคารอื่น/ของเดิม (K-ePocket, Maybank, กฎ ธปท.) ไม่มี เพราะของเขามีแค่ "เตือน/บล็อกตอนเกินวงเงิน" เฉยๆ ไม่มี architecture หลายกระเป๋าที่ดึงเงินข้ามกันแบบนี้ — เป็น novelty claim ที่แข็งแรงกว่าแค่ "มี daily limit"
- **กระเป๋านิรภัย** → พิชเป็น **"ฟีเจอร์หน่วงเพื่อการออม"** ที่ ePocket เดิมไม่มี (ต่างจากกระเป๋าปกติตรงต้องรอถึงจะใช้ได้) ประโยชน์หลักคือมีเวลาคิดตัดสินใจนานขึ้น + เห็นพฤติกรรมใช้เงินตัวเองชัดขึ้น ส่วนกันโกงเป็นผลทางอ้อมที่พูดถึงได้แต่ต้องพูดแบบมีเงื่อนไข ("อาจช่วยลดโอกาส...") ไม่ใช่พิชเป็น "เราคิดค้นระบบกันโกงด้วยการหน่วงเงิน" เพราะจุดนั้นซ้ำทั้ง Maybank/Jago และซ้ำกฎ ธปท. ที่บังคับทุกธนาคารไทยอยู่แล้ว (รายละเอียด section 3)

## 2. เนื้อหาสำหรับ 1-Page Pitch

### Problem Statement
- First Jobbers ไทยจำนวนมากเงินเดือนหมดก่อนสิ้นเดือนโดยไม่รู้ตัวว่าเงินไปไหน
- คนอายุ 21–30 (โดยเฉพาะผู้หญิง) เป็นกลุ่มเหยื่อหลักของ scam ในไทย ความเสียหายระดับประเทศสูงมาก (หมื่นล้าน-แสนล้านบาท/ปี) และโตต่อเนื่อง — **online job scam** (หลอกสมัครงาน/โอนมัดจำ) เป็นรูปแบบที่เล็งกลุ่มคนหางาน/first jobber โดยตรง
- เงินเดือนแรกเข้าของบัณฑิตจบใหม่ไทยส่วนใหญ่อยู่ช่วง 15,001–30,000 บาท ขณะค่าครองชีพเมืองสูง ทำให้บริหารเงินเดือนชนเดือนยาก

> ⚠️ ตัวเลข "84% เงินเดือนหมดเป็นศูนย์" / "52,000 บาทต่อครั้ง" จาก reference เดิม **ยังไม่เจอ source ยืนยัน** — ต้องเช็ค source จริงหรือเปลี่ยนไปใช้ตัวเลขที่มี source (ดู References) ก่อนใส่สไลด์จริง

### Proposed Solution
Pace = auto-split เงินเดือนเข้า ePocket 3 บัญชี + เติมกระเป๋าใช้จ่ายรายวันอัตโนมัติทุกวัน + กระเป๋านิรภัยหน่วงเวลา (รายละเอียด section 1)

### Target Users
K PLUS users อายุ **22–30 ปี** (ตรงตาม detail.md) First Jobbers รายได้ปานกลาง-จำกัด กลุ่มเช่าบ้าน/คอนโดในเมือง มีรายรับสม่ำเสมอแต่จัดสรรเงินเองไม่ทัน

### Value Proposition
- **ผู้ใช้:** ไม่ต้องมานั่งแบ่งเงินเอง + เห็นเงินออมโตจริงแบบอัตโนมัติ + มีเวลาคิดตัดสินใจนานขึ้นก่อนใช้เงินก้อนออม + เห็นพฤติกรรมใช้เงินตัวเองชัดขึ้น (ซึ่งอาจช่วยลดโอกาสโดน scam ได้บ้างเป็นผลพลอยได้)
- **K PLUS:** เพิ่ม engagement รายวัน (เปิดแอปดูกระเป๋ารายวัน/นิรภัย), ต่อยอดขาย product ออมทรัพย์จาก data พฤติกรรม, ลดความเสียหาย fraud บาง scenario บน platform

(แบงก์ชาติ) — กฎบังคับทุกธนาคารไทย** | บังคับตั้งวงเงินโอน/จ่าย mobile banking ตาม risk profile (เช่น 50,000 บ./วัน) ต้อง comply ทุกแบงก์ภายในสิ้นปี 2025 + กำลังผลักดันมาตรการ**หน่วงเงิน 72 ชม.** สำหรับโอน >10,000 บาท + ธนาคารระงับธุรกรรมต้องสงสัยได้เองอยู่แล้ว | **นี่คือความเสี่ยงใหญ่สุด** — "วงเงินรายวัน" กับ "หน่วงเวลาโอน" กำลังเป็น**มาตรฐานบังคับทั้งอุตสาหกรรม** ไม่ใช่จุดขายที่ทำให้ทีมดูใหม่ได้อีก ต้องเลี่ยงพิชสองจุดนี้เป็นหลัก (ดูข้อ "ลำดับจุดขาย" ด้านบน) แต่ยังมีจุดต่างเชิงกลไกจริง: ของ ธปท. หน่วงตาม **จำนวนเงิน/risk score** (เกินเกณฑ์ถึงหน่วง) ส่วนกระเป๋านิรภัยของ Pace หน่วง**ทุกจำนวนเท่ากันหมด** เพราะผูกกับ **ประเภทบัญชี** (เป็นบัญชีออม) ไม่ใช่ผูกกับความเสี่ยงของธุรกรรม — ถอน 1,000 บาทก็หน่วงเหมือนถอนหลักหมื่น พิชจุดนี้ได้ว่าเป็นกฎคนละแบบ ไม่ใช่แค่ทำซ้ำของเดิม |

### ✅ อ่านโจทย์ให้ดี: "ใหม่สำหรับ K PLUS" ไม่ใช่ "ใหม่ระดับโลก"

detail.md เขียนชัดว่า "คิด Feature, Function หรือ Solution **ใหม่สำหรับ K PLUS**" / อังกฤษ "Design a **new feature...for K PLUS**" — **ไม่ได้ขอสิ่งที่ไม่เคยมีในโลก** Pace ผ่านเกณฑ์นี้เต็มๆ เพราะ K PLUS ไม่มีสักกลไกเดียวจาก 3 กลไก (ePocket ปัจจุบัน manual ล้วน)

และเกณฑ์ตัดสินที่โจทย์ระบุคือ **ความเข้าใจในปัญหา + ความเหมาะสมของ Solution + การประยุกต์ใช้ทักษะของ Track** — **ไม่มีคำว่า "ความใหม่/originality" เป็นเกณฑ์เลย**

ดังนั้นการเช็คคู่แข่งทั้งหมดข้างล่างนี้ **ไม่ใช่เพื่อพิสูจน์ว่าเราใหม่** แต่เพื่อ (1) กันพูดเกินจริงแล้วโดนจับได้ (2) ตอบให้ได้ว่าต่างจาก MAKE/ePocket ยังไง (3) โชว์ว่าทำการบ้านมาจริง = ได้คะแนน "ความเข้าใจปัญหา" ตรงๆ

### 🎯 สิ่งที่เหลือเป็นของใหม่จริงๆ หลังเช็คครบทุกเจ้าแล้ว

หลังเทียบกับ K-ePocket, MAKE by KBank, Qapital/Digit, Maybank/Jago/BCA และกฎ ธปท. ครบแล้ว **เหลือ 3 อย่างที่ยังไม่มีใครทำ**:

1. **Cooldown หน่วงเวลาตอนถอน** — ทุกเจ้าที่ "ล็อกเงิน" ได้ (MAKE, Maybank, Jago) ปลดล็อกแล้วใช้เงินได้**ทันที** หรือไม่ก็ต้องไปสาขา ไม่มีใครใช้ "รอ 24-48 ชม. แล้วปล่อยอัตโนมัติ" แบบ Pace
2. **Daily Auto-Refill จากกระเป๋าแม่ + backfill real-time ตอนใช้เกิน** — ไม่มีใครมี architecture หลายกระเป๋าที่ดึงเงินข้ามกันแบบ atomic พร้อมโชว์ผลกระทบยอดกระเป๋าแม่ทันที
3. **เอาทั้งหมดมาไว้ใน K PLUS** — MAKE ทำได้บางส่วนแต่เป็นแอปแยก, Qapital เป็นแอปต่างประเทศ, ePocket ใน K PLUS ยังเป็น manual ล้วน

**สรุป (แก้ไขแล้ว):** อย่าพิชว่า "เรามีวงเงินรายวัน/หน่วงเวลาโอน" เป็นจุดขาย เพราะซ้ำทั้งของเดิม (ePocket), คู่แข่งต่างประเทศ, และกฎหมายบังคับในประเทศ — **และอย่าพิช "auto-split" ว่าไม่มีใครทำเลยในโลก** เพราะ Qapital/Digit ทำมาก่อนแล้วหลายปี จุดขายจริงที่เหลือคือ **combination**: ไม่มีธนาคารไทยไหนทำ auto-split-on-salary-credit + ผูกกับ ePocket เดิม + รวมกับ Daily Auto-Refill และ Vault ในระบบเดียวกัน — พิชเป็น "การรวมกลไกที่ไม่มีใครทำแบบนี้ในไทย" ไม่ใช่ "เราคิดค้น auto-split ขึ้นมาเป็นคนแรกของโลก"

## 4. Track 1 Perspective: Develop → Test → Ensure Quality

### Scope PoC (ทำได้จริงในเวลาจำกัด)
ไม่ต้องต่อ core banking จริง ใช้ mock data พอ demo:
- Mock event "เงินเดือนเข้า" → rule engine สร้างรายการโอนเข้าแต่ละ ePocket อัตโนมัติ
- ขอถอนจากกระเป๋านิรภัย → state "pending cooldown" → mock notification → confirm/cancel
- Mock cron "เที่ยงคืน" → top-up กระเป๋าใช้จ่ายรายวันจากบัญชีเงินรายเดือน (เติมแค่ส่วนต่างจากเป้าหมาย), จำลองใช้จ่ายเกินเป้า → ดึงชดเชย real-time + ขึ้น warning (พร้อมยอดคงเหลือบัญชีเงินรายเดือน) + บันทึกสถิติ ไม่ hard block (ยกเว้นบัญชีเงินรายเดือนหมดจริง)
- หน้าหลัก demo ต้องโชว์ยอด **กระเป๋ารายวัน + บัญชีเงินรายเดือน** คู่กันตลอด ไม่ใช่โชว์แค่กระเป๋ารายวันอย่างเดียว

### Architecture
- Frontend: mobile-web prototype พอ demo UI
- Backend: REST API เบาๆ, rule engine แยก module ชัดเจนเพื่อ unit test ง่าย
- Data: fixture/mock DB + เขียน adapter interface ไว้เผื่อต่อของจริงภายหลัง
- **สำคัญ: cooldown state ต้อง authoritative ที่ backend เท่านั้น** client (มือถือ) แค่แสดง countdown จาก timestamp ที่ server ส่งมา ห้ามคำนวณเวลาที่ปล่อยเงินจากนาฬิกาเครื่องผู้ใช้ ไม่งั้นปลอมเวลาเครื่อง/ยิง API ตรงเพื่อปลดล็อกก่อนกำหนดได้

### แผนทดสอบคุณภาพ (จุดขายของ Track 1)
1. **Unit Test** — สัดส่วน auto-split ต้องรวม 100%, เงินเดือนน้อยกว่าบิลรวม, เศษสตางค์จากการหาร, ถอนจากนิรภัยจำนวนน้อย (เช่น 1,000 บาท) ต้องโดน cooldown เหมือนจำนวนมาก (ยืนยันว่ากฎผูกกับประเภทบัญชี ไม่ใช่ threshold ตามจำนวนเงิน), คำนวณ top-up รายวันถูกต้อง (เติมแค่ส่วนต่าง ไม่ทับยอด carry-over เดิม, ยอดติดลบคำนวณชดเชยถูก)
2. **Integration Test** — flow ขอถอนจากนิรภัย → pending cooldown → auto-release เมื่อครบเวลา, กดยกเลิกระหว่าง cooldown → เงินอยู่นิรภัยต่อ, ขอถอนซ้ำระหว่างมี request pending → ต้องรวมเป็นคำขอเดียวและนับเวลาใหม่ (ไม่ใช่ปล่อยตามเวลาคำขอแรก), notification ยิงถูกจังหวะ (ตอนขอถอน + ก่อนปล่อยเงิน ~1 ชม.), flow ใช้จ่ายเกินเป้ารายวัน → ดึงชดเชยจากบัญชีเงินรายเดือน real-time + ธุรกรรมผ่าน + warning **แสดงยอดคงเหลือบัญชีเงินรายเดือนถูกต้องหลังหัก** + สถิติอัพเดตถูกต้อง, edge case บัญชีเงินรายเดือนไม่พอ → ธุรกรรมถูกปฏิเสธ (ไม่ crash/ไม่เงียบ), หน้าหลักแสดงยอดกระเป๋ารายวัน+บัญชีเงินรายเดือนตรงกับ backend เสมอหลังทุกธุรกรรม (ไม่ค้าง/ไม่ผิด sync), ตัวเลข "เกินเป้าไปแล้ว X บาท" ของวันนั้นค้างแสดงถูกต้องตลอดวัน + รีเซ็ตกลับเป็น 0 ตอนเที่ยงคืนพร้อมรอบ top-up ใหม่
3. **Consistency/No-Bypass Test** — ยืนยันว่า cooldown ใช้เหมือนกัน**ทุกกรณีไม่มีข้อยกเว้น** ไม่ว่าจำนวนเงิน เวลา หรือความถี่การถอน (ตามหลัก "หน่วงเพื่อการออม" ไม่ใช่ risk-based detection) — ทดสอบว่าไม่มีช่องบายพาส เช่น ถอนผ่านช่องทางอื่น, เปลี่ยนเวลาเครื่อง, เรียก API ตรงข้าม UI *(หมายเหตุ: ไม่ใช่ fraud-detection test เพราะระบบไม่มี risk engine ตรวจจับพฤติกรรม — เป็นแค่กฎหน่วงตายตัวตามประเภทบัญชี)*
4. **Usability/Feasibility Test เล็กๆ** — ให้กลุ่มตัวอย่าง first jobber 5–8 คนลองใช้ เก็บ feedback สัดส่วน auto-split และความยาว cooldown + เก็บ **อัตราการกดยกเลิกคำขอถอนระหว่าง cooldown** เป็นตัวชี้วัดเชิงพฤติกรรมว่า "เวลาคิดที่เพิ่มขึ้น" ช่วยให้เปลี่ยนใจจริงไหม (หลักฐานจับต้องได้ของประโยชน์ทางอ้อมข้อ 1–3 ด้านบน)
5. **Non-functional** — response time ตอนเงินเดือนเข้า, ทดสอบ concurrent user ระดับ PoC

### Pitch Narrative
Problem → Feature (auto-split = novelty claim, vault = ฟีเจอร์หน่วงเพื่อการออม ให้เวลาคิด+เห็นพฤติกรรมใช้เงินตัวเอง กันโกงเป็นผลพลอยได้) → Develop ยังไง → Test/Quality ยังไง → Value Proposition + ผล demo/feasibility
